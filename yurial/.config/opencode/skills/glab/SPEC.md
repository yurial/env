# Skill `glab`

Status: stable
Spec source of truth for: the `glab` skill — the SKILL.md guide «glab: GitLab CLI — typical workflows and traps» (working with GitLab from the command line via glab, the GitLab CLI) and the bundled gitlab-tools toolkit (`tools/` next to SKILL.md)
Reference: glab

## Overview

The `glab` skill governs how an agent works with GitLab from the command line via glab, the GitLab CLI. The skill is instructions to the agent: practical rules for repository context, authorization, non-interactive usage, role-based MR lists, drafts, typical MR operations, machine-generated comments, MR descriptions and review comments (the description/commit-message language pair, reading line-anchored discussions, posting line-level comments, batch posting with line-anchor validation against diff hunks and diff_refs freshness), the draft review flow (draft notes created first, then published all at once with a single call), replying in discussions with the GraphQL fallback and thread resolution state, the REST API via `glab api` (fields, request bodies, URL-encoded paths, pagination) and GraphQL via `glab api graphql`, HTTP error disambiguation, multi-host auth diagnostics, git-over-HTTP(S) authentication independent from API tokens, reading review comments via the discussions endpoint, issues, and CI/CD pipelines and jobs. The skill also fixes the author-side workflow for processing incoming review comments: each comment is handled individually, new comments are selected by a full-list re-fetch rather than a time threshold, and a thread is resolved only after a fix or a reasoned reply (R11.1..R11.4). The skill also ships a mechanical layer: the gitlab-tools toolkit (`tools/` next to SKILL.md) — bash+python3 scripts over `glab api` implementing global role-based MR listings with the mandatory scope=all, MR update polling with a state marker, the fast boolean "any updates on this MR?" timer check (`mr-has-updates.sh`), thread dumps, single line-anchored comments, batch draft review with a safe publish, discussion replies, single-thread resolve, read-only post-publish verification of posted comments, the live token-health probe (`mr-auth-probe.sh`), the MR card (`mr-card.sh`), and the true local MR diff (`mr-diff.sh`) as the preferred mechanical path for these operations — covering the whole MR watcher loop (probe → card → diff → threads → comments → polling → publish → verification) without raw glab calls — while raw glab remains the path for everything else and for understanding the underlying API semantics (R12.1, R12.2, R12.4, R12.5, R13.9..R13.17). Every command, flag, and behavioral claim in the skill must be verified against the help output of the installed glab version — `glab help`, `glab <command> --help` — or against live behavior on an authenticated host; the skill states the version it was verified against (R14.1, R14.2). Behavior observed only on a specific instance is marked instance-dependent in the skill (R14.4). Traps — conditions that fail silently or mislead (scope=all, iid vs id, flag collisions, HTTP error shapes, exit code `0` on HTTP errors, line anchors on context lines, silently dropped discussion replies) — are highlighted as critical in the skill (R14.6).

The skill activates when working with GitLab from the command line via glab: listing, viewing, creating, checking out, approving, and merging merge requests; writing MR descriptions and reading and posting MR review comments; batch posting of review comments (line-anchor validation against diff hunks, diff_refs freshness, canary-first protocol); review comments via draft review (draft notes, publish all at once); discussion replies via the GraphQL fallback; thread resolution state (`blocking_discussions_resolved`); processing incoming review comments as the MR author (individual comment workflow, resolve discipline); filtering MRs by role (reviewer, assignee, author); draft/WIP MRs; managing issues; checking CI/CD pipelines and jobs; calling the GitLab REST API via `glab api`; non-interactive glab usage and interpreting glab errors; diagnosing multi-host authentication (stale stored tokens, `--hostname` scoping); git-over-HTTP(S) push/fetch authentication as distinct from API-token authentication; reading MR review comments via the discussions endpoint; running the bundled gitlab-tools scripts (`tools/` next to the skill) as the preferred mechanical path for their covered operations — a global MR listing by role with the scope=all trap encapsulated, MR update polling with a state marker, the fast boolean has-updates timer check, the timer/watcher gate scenario over it, the live token-health probe, the MR card, the true local MR diff, thread dumps, single line-anchored comments, batch draft review with the stray-draft guard and single-id publish, discussion replies with the GraphQL fallback, single-thread resolve, verdict-plan posting, and read-only post-publish verification of posted comments — pending-draft count, max note id, expected-body/anchor verification (R12.2, R12.4, R12.5, R13.9..R13.17). The canonical trigger text is the frontmatter `description` (Interface); the activation scope grows together with the coverage requirements (R14.7). The skill does not apply to plain git workflows, other forges, or GitLab web UI operations (Scope, Out).

## Definitions

- `glab/repository-context` — the git repository of the current working directory; `glab mr`, `glab issue`, `glab ci` commands derive host and project from its `git remote` (usually `origin`) (R1.1).
- `glab/global-endpoint` — a top-level REST endpoint (`merge_requests`, `issues`) queried via `glab api` across all accessible projects; contrasted with project-scoped commands (R3.1, R3.2).
- `glab/iid` — the per-project number of an MR or issue, used in URLs and glab arguments; distinct from the globally unique `id` (R3.3).
- `glab/draft-mr` — an MR marked not ready: `Draft:`/`WIP:` title prefix, API field `work_in_progress: true` (R3.4).
- `glab/url-encoded-project-path` — the `<group>%2F<project>` form of a project path in REST URLs; a raw `/` splits URL segments and breaks route resolution (R6.3).
- `glab/placeholder` — an angle-bracket identifier (`<group/project>`, `<username>`, `<iid>`, ...) standing for a real value; real identifiers must not appear in the skill (R14.3).
- `glab/machine-readable-output` — output intended for programmatic parsing: raw JSON from `glab api`, the `ids`/`urls` formats of `glab issue list` (R2.2).
- `glab/line-anchored-comment` — a discussion note attached to specific diff lines via a `position` object (`position_type` `"text"`; `new_line`/`new_path` for the new side, `old_line`/`old_path` for the old side; `line_range` spans a block of lines); contrasted with a top-level MR note, which has no `position` (R8.2, R8.3).
- `glab/trap` — a condition that fails silently or returns misleading data (scope=all, iid vs id, flag collisions, HTTP `404` shapes, exit code `0` on HTTP errors); traps are highlighted in the skill (R14.6).
- `glab/discussion-thread` — a `discussions`-endpoint object grouping the notes of one review conversation; its notes carry `position` for diff-anchored comments and `system: true` marks service notes (R8.4).
- `glab/review-comment-processing` — the author-side workflow for incoming review comments: fetching all discussions, reading each comment individually at its anchored lines, deciding per comment between a change and a reasoned reply, and resolving the thread only after one of the two (R11.1..R11.4).
- `glab/hunk-range` — the new-side line span of one diff hunk of a file (the `@@ +<start>,<count> @@` header); a line-anchored position is accepted only on lines inside hunk ranges — context lines are rejected with HTTP `400` (R9.1).
- `glab/outdated-note` — a diff-anchored note created against a superseded diff version; GitLab marks it outdated when `diff_refs` move after the note was created (R9.2).
- `glab/draft-note` — a pending, unpublished comment on an MR managed via the `draft_notes` API; before publishing it is visible only to its author (per GitLab docs); carries the same `position` object as a line-anchored comment and publishes into a real note/discussion (R10.1).
- `glab/publish-all` — the single `POST .../draft_notes/bulk_publish` call that turns all pending draft notes of the current user on an MR into real notes/discussions at once; the counterpart of per-comment posting straight into discussions (R10.1, R10.4).
- `glab/gitlab-tools` — the bundled bash+python3 toolkit in `tools/` next to SKILL.md implementing the skill's review workflows over `glab api`; the preferred mechanical path for its covered operations, with `tools/README.md` as its contract documentation (R12.1, R12.2).
- `glab/state-marker` — the JSON file written by `mr-updates.sh --state` (MR head sha + short_id, max note id/created_at, `"schema": 3`); the next run reports only the delta; the schema evolves additively and a masked sha is never stored as a cutoff (R13.1, R13.14, R15.7).
- `glab/has-updates-marker` — the JSON state file of `mr-has-updates.sh --state` (default `<tools>/.state/has-updates/<project-without-slashes>__<iid>.json`, `"schema": 4`): head short id, max note id, unresolved note ids, discussion ids, MR state/draft, title/description length+hash pairs, reviewers/approvals, merge statuses, pipeline id+status — no secrets and no full `40-hex` shas; additive, atomic, rewritten only on a baseline or a detected change (R13.11, R13.14).
- `glab/stray-draft-guard` — the refusal of `mr-draft-review.sh` to create drafts when the user already has pending draft notes on the MR — mixing runs makes publish steps dangerous; escaped only with `--ignore-stray` (R13.4; invariant R15.6).
- `glab/post-publish-verification` — the read-only after-the-fact check that expected comment bodies are really posted: byte-exact body match plus anchor (or reply-inside-thread) match, together with the pending-draft count and the max note id baseline; mechanized by the bundled `mr-verify-posted.sh` (R13.9).
- `glab/configured-comment-prefix` — the marker text every machine-generated comment must begin with: the value of `GITLAB_COMMENT_PREFIX`, resolved environment > `config.sh` > the built-in default `[ai] `; prescribed per host/repository by its owner; the honesty-marker rule (R5.1, invariant R15.1) applies to the configured text unchanged (R12.5).

## Requirements

- R1. Repository context and authorization:
- R1.1. verification=manual; Repository context. The skill documents: `glab mr`, `glab issue`, `glab ci` commands require a git repository — host and project derive from `git remote` (usually `origin`); outside a repository they fail with `fatal: not a git repository ...` and exit code `1` — a context error, not an empty result; the `-R <group/project>` flag selects another project (formats `<group>/<project>`, nested `<group>/<subgroup>/<project>`, per glab help also a full URL or git URL) and exists on all `glab mr`, `glab issue`, `glab ci` commands; `glab api` and `glab auth status` work outside repositories — inside a repository its authenticated host is used, otherwise the default host (`--hostname` overrides, for `glab api`).
- R1.2. verification=manual; Authorization. The skill documents: `glab auth status` (works from any directory) as the pre-flight check; `✓ Logged in ... as <username>` marks a valid token, `x`/`!` lines mark token problems as indicators to check — not a verdict (they can coexist with a working token; the verdict is a live API call — R1.3) — and with a bad token API calls return `401`; non-interactive login `glab auth login --hostname <host> --stdin` (token on standard input; `-t/--token` exists but puts the secret in the command line); minimum token scopes `api`, `write_repository`; environment variables `GITLAB_TOKEN` (token for API requests, overrides stored credentials) and `GITLAB_HOST`/`GL_HOST` (self-managed host URL).
- R1.3. verification=manual; Multi-host auth diagnostics (trap). The skill documents: on a machine with several configured hosts `glab auth status` prints a block per host, and a stored token may be present yet stale — a per-host block showing both `Token: ****` and `! Invalid token provided` may mean the stored token is stale/expired and API calls to that host return `401`; `glab auth status` without `--hostname` may check a different host than the one the API calls use, so diagnosis of a specific host passes `--hostname <host>`; instance-dependent (observed `2026-10-26` on GitLab 18.8.11-ee): within one host block the lines `✓ Logged in ... as <username>` (itself derived from a successful `/user` call) and `! Invalid token provided` may coexist while the token works — the immediately following live API call answered `200` — so `auth status` output is a hint to check, never a verdict: the token's health is decided only by a live API call (a cheap `glab api user --hostname <host>`; `200` = working, `401` = broken), and re-login is performed only after a real `401` from a live call, never on an `!` line alone; recovery is re-login or a fresh `GITLAB_TOKEN` (R1.2), and `glab api` still exits `0` on the `401` (R2.2).
- R1.4. verification=manual; Git-over-HTTP(S) auth is independent of the API token (trap). The skill documents: `glab` covers the API, while `git push`/`git fetch` over HTTPS authenticate separately and a working API token may be rejected for git-over-HTTP on a self-managed instance (`remote: HTTP Basic: Access denied`); the symptom pair "API works (`200`), HTTPS push denied" and "SSH push fails with Permission denied (publickey)" is documented; the recovery order is SSH remotes with a loaded agent key (`ssh -T git@<host>` as the check), then a token-as-password HTTPS URL (`https://oauth2:<token>@<host>/...`) only after verifying the instance accepts it, and restoring the remote URL afterwards; a token must not remain embedded in a remote URL (`.git/config` plain text).
- R2. Non-interactive usage and machine-readable output:
- R2.1. verification=manual; Non-interactive usage. The skill documents: `NO_PROMPT=1` disables interactive prompts; mutating commands support `-y/--yes` to skip the submission confirmation (verified for `mr create`, `mr merge`, `issue create`); explicit flags are preferred over prompts (`--no-editor` avoids opening an editor); in scripts and agent runs long flag names are mandatory because short flags collide across subcommands — `-F` is `--field` in `glab api` but `--output-format` in `glab issue list`, `-f` is `--raw-field` in `glab api` but `--fill` in `glab mr create`; `NO_COLOR` removes ANSI escape sequences from parsed output; `GITLAB_TOKEN`/`GITLAB_HOST` (R1.2) supply token and host non-interactively.
- R2.2. verification=manual; Machine-readable output. The skill documents: `glab api` is the reliable JSON source (raw JSON to standard output); `glab mr list` has no JSON output format in glab 1.36.0 — for JSON, query the API instead; `glab issue list -F ids`/`-F urls` print one identifier/one web URL per line; `glab api` exits `0` even on HTTP errors — `401`/`404`, and `400` on POST requests (R9.3) — the error is visible in the stderr line `glab: <message> (HTTP <code>)` and in the response body, so parsing must check those, not the exit code; `glab mr`/`glab issue`/`glab ci` commands exit `1` on context errors (R1.1).
- R3. MR lists, drafts, and identifier discipline:
- R3.1. verification=manual; MR lists by role. The skill documents both levels. Inside a repository/group: `glab mr list --reviewer=@me|--author=@me|--assignee=@me` (`@me` is the current user; also `-g <group>`); default page of `30` records, `-P`/`-p` control per-page/page. Across all accessible projects: the global endpoint `merge_requests?reviewer_username=<username>&state=opened&scope=all` (likewise `author_username`, `assignee_username`); the response is a JSON array parsed with jq or python; useful fields: `iid`, `title`, `state`, `references.full`, `web_url`, `work_in_progress`, `author`.
- R3.2. verification=manual; The scope=all trap (critical). The skill documents: without `scope`, the global `merge_requests` endpoint defaults to `created_by_me` — a role-filtered query silently returns only MRs created by the caller (often an empty list) instead of all matching MRs; any global MR search by `reviewer_username`/`author_username`/`assignee_username` must carry `&scope=all`; the global `issues` endpoint carries the same documented default scope and needs `&scope=all` as well; on an empty result, before reporting "no MRs", check in order: `scope=all` present; `state` correct (`opened` excludes `merged`/`closed`); the right project/group searched.
- R3.3. verification=manual; iid vs the global number. The skill documents: `iid` is the per-project MR number used in the URL and in `glab mr <subcommand> <iid>`; only `id` is globally unique; the same `iid` in different projects means different MRs; `404 Not Found` from `glab mr view <N>` more often means "wrong project" (host/project taken from the current repository) than "the MR does not exist"; numeric references require working from that project's repository or `-R <group/project>`.
- R3.4. verification=manual; Drafts. The skill documents: a draft MR has a `Draft:`/`WIP:` title prefix and the API field `work_in_progress: true`; filtering via `glab mr list -d/--draft` or the API parameter `wip=yes`/`wip=no`; the draft status is always shown in reports to the user (a draft is usually not ready for review/merge).
- R4. Typical MR operations:
- R4.1. verification=manual; Typical MR operations. The skill documents the working set — `view`, `diff`, `checkout`, `create --fill`, `approve`, `merge` (useful flags `-y`, `--squash`, `-d`), `close`, `reopen` — and that an MR is addressed by `<iid>`, by its source branch name, or (without an argument) by the MR of the current branch; all commands accept `-R`.
- R4.2. verification=manual; Delete source branch on merge. The skill documents: an MR is created with the «delete source branch on merge» setting — `glab mr create --remove-source-branch`; the flag is set at creation so that the branch deletion is carried by the MR and happens however the MR is later merged; short-flag collision (R2.1): in `mr create` `-d` is `--description`, so only the long form sets the branch flag, while in `mr merge` `-d` is `--remove-source-branch`; the merge-time equivalent — `glab mr merge <iid> -d`/`--remove-source-branch` — is documented as the fallback for an MR created without the flag; both flags verified against glab 1.36.0 help.
- R5. Machine-generated comment prefix:
- R5.1. verification=manual; Comments — mandatory `[ai] ` prefix. The skill documents: every comment posted via glab — a note on an MR, a comment on an issue, a reply in a discussion — must begin with the prefix `[ai] ` (brackets plus a trailing space) followed by the comment text; in a multi-line comment the first line still begins with the prefix; commands: `glab mr note <iid> -m "[ai] <comment text>"`, `glab issue note <iid> -m "[ai] <comment text>"`, and a discussion reply via the API with a `body` field carrying the prefix.
- R6. glab api mechanics and HTTP errors:
- R6.1. verification=manual; API pagination. The skill documents: `glab api` returns a single page (`20` records by default); complete lists require `&per_page=100` plus walking `&page=2`, `&page=3`, ... — or the `--paginate` flag, which fetches all pages sequentially; a missing "tail" of a large list is the typical symptom of forgotten pagination.
- R6.2. verification=manual; API fields and bodies. The skill documents, per glab help: `-f/--raw-field key=value` adds a string parameter (no type conversion); `-F/--field key=value` adds a typed parameter — literal `true`/`false`/`null` and integers convert to JSON types, a value starting with `@` is read from that file and `-` from standard input (the standard way to pass multiline text); any field switches the default method from GET to POST, `-X/--method` overrides; a raw request body is passed via `--input <file>` (`-` = standard input), and in this mode `--field`/`--raw-field` flags are serialized into URL query parameters; `-H/--header` adds HTTP headers.
- R6.3. verification=manual; URL-encoded project paths. The skill documents: inside a repository the `:fullpath` placeholder is replaced with the current project; outside it (or for another project) the project path in REST URLs must be URL-encoded — `projects/<group>%2F<project>/...`; a raw `/` splits the path and yields a generic `{"error":"404 Not Found"}` even when the project exists, while the encoded form for a missing project answers `{"message":"404 Project Not Found"}` — the two `404` body shapes distinguish a broken path from a missing project.
- R6.4. verification=manual; HTTP error disambiguation. The skill documents: `401` — token missing, invalid, or expired for that host → check `glab auth status` (a hint, not a verdict — R1.3; the live `401` is itself the verdict that justifies the re-login), re-login; `403` — the token is valid but the account lacks permission for the action (GitLab REST semantics); `404` — most often a wrong project (repository context, missing `-R`, unencoded path per R6.3), only then a nonexistent resource — consistent with the iid≠id rule (R3.3); and that `glab api` exits `0` on all of these (R2.2).
- R6.5. verification=manual; `glab api` scoping: no `-R` flag. The skill documents: `glab api` has no `-R/--repo` flag (verified against glab 1.36.0 help); the project is always part of the URL — `:fullpath` inside the repository or the URL-encoded path outside it (R6.3) — and the host is selected with `--hostname <host>`; `-R` exists on `glab mr`, `glab issue`, `glab ci` commands, not on `glab api`.
- R7. Issues and CI/CD pipelines and jobs:
- R7.1. verification=manual; Issues. The skill documents the verified subset: `glab issue list` — filters `--assignee=@me`, `--author=<username>`, `-A`, `-g <group>`, labels, search; machine-friendly formats `-F ids`/`-F urls`; `glab issue view <iid>` (also accepts a full issue URL); non-interactive creation `glab issue create -t "<title>" -d "<description>" -y`; `glab issue note` with the mandatory prefix (R5.1); `glab issue close`/`glab issue reopen`. iid semantics and the repository-context rules apply to issues exactly as to MRs (R1.1, R3.3); the global `issues` endpoint requires `scope=all` (R3.2).
- R7.2. verification=manual; CI/CD pipelines and jobs. The skill documents the verified subset: `glab ci status` — pipeline of the current branch, flags `-b <branch>`, `-c` (compact), `-l` (live); `glab ci list` — `--status=<status>` filter (running|pending|success|failed|canceled|skipped|...); `glab ci trace <job-id>|<job-name>` — live job log, flags `-b`, `-p <pipeline-id>`; `glab ci retry <job-id>|<job-name>` — retry operates at the job level, not the pipeline level; the aliases `glab pipe`/`glab pipeline`; that without an argument `trace`/`retry` prompt interactively to select a job; repository context and `-R` apply (R1.1).
- R8. MR descriptions, review-comment reading, replies, and thread state:
- R8.1. verification=manual; MR description and commit-message languages. The skill documents: the MR description is written in Russian and describes both the problem being solved and the way this problem is solved; the MR commit message is written in English and semantically mirrors the Russian description. The description is passed explicitly — `glab mr create -t "<title>" -d "<description>"` — and corrected later with `glab mr update <iid> -d "<description>"`; the `--fill` caveat: `--fill` takes the title/description from commit info (English commit messages), which does not satisfy the required language split, so it is not used to produce the description; the English commit message is set at merge time — `glab mr merge <iid> -m "<message>"` (with `-s/--squash` — `--squash-message "<message>"`).
- R8.2. verification=manual; Reading MR comments with line context. The skill documents: when reading MR discussions/comments, always resolve the line numbers a comment is anchored to and read the code at those lines (`glab mr diff <iid>` or the checked-out MR branch) before replying or acting on the comment; the quick view is `glab mr view <iid> --comments`, the machine-readable form is `glab api "projects/:fullpath/merge_requests/<iid>/discussions"` (pagination per R6.1); a diff-anchored note carries a `position` object — `position_type` `"text"`, `new_line`/`new_path` for the new side, `old_line`/`old_path` for the old side, `line_range` when the note spans a block of lines — while a note without `position` is a top-level MR note.
- R8.3. verification=manual; Line-level comments preferred. The skill documents: a comment about specific code is posted as a note anchored to that line/block — a line-anchored comment (Definitions) — not as a top-level note; `glab mr note` posts only top-level notes (in glab 1.36.0 it has no line anchoring), so a line-anchored comment is created via the REST API: `POST projects/:id/merge_requests/<iid>/discussions` with a `body` and a `position` — `base_sha`/`start_sha`/`head_sha` taken from the single-MR endpoint's `diff_refs` (the list endpoint returns `diff_refs: null`), `position_type` `"text"`, `new_path`+`new_line` (or `old_path`+`old_line`) — passed as a JSON body via `--input` (R6.2); the mandatory `[ai] ` prefix (R5.1, R15.1) applies to these comments as to every other.
- R8.4. verification=manual; Review comments are read via the discussions endpoint (trap). The skill documents: `GET .../merge_requests/<iid>/notes` returns a flat mixed list of system and user notes without file/line context — the right endpoint for review comments is `GET .../merge_requests/<iid>/discussions`, where each discussion is a thread whose notes carry the text plus, for diff-anchored notes, the `position` object (R8.2); system notes (`system: true`) are skipped; a note with `position` is line-anchored, without — top-level; replies go into the same thread via `POST .../discussions/<discussion_id>/notes` (R5.1, R8.3); the documented workflow is fetch discussions, list non-system notes with their anchored `new_path:new_line`, read the code at those lines (R8.2), reply per discussion with the mandatory prefix (R15.1).
- R8.5. verification=manual; Discussion replies via the GraphQL fallback (trap, instance-dependent). The skill documents: the documented REST reply path is `POST .../discussions/<discussion_id>/notes` (R5.1, R8.4), but on some instances (observed on GitLab 18.7.7-ee) it answers `404` while the `in_reply_to_discussion_id` parameter of `POST .../notes` is silently ignored — the reply lands as a separate orphan discussion; the working path on such an instance is the GraphQL mutation `createNote` with a `discussionId` of the form `gid://gitlab/Discussion/<discussion_id>`, sent via `glab api graphql` (the `graphql` endpoint is documented in `glab api --help`; fields other than `query`/`operationName` are passed as GraphQL variables, so the object `input` is passed via a raw `--input` body per R6.2); the mandatory prefix (R5.1, R15.1) applies to GraphQL replies; the REST-`404` behavior is marked instance-dependent (R14.4).
- R8.6. verification=manual; Thread resolution state (instance-dependent). The skill documents: in the discussions listing a discussion-level `resolved` field may be absent (observed on GitLab 18.7.7-ee); a thread counts as resolved exactly when every non-system note in it has `resolved: true`; the MR-level merge-readiness signal for open threads is `blocking_discussions_resolved` of the single-MR endpoint, not a discussion-level flag.
- R8.7. verification=manual; Discussions listing pagination. The skill documents: `GET .../discussions` is paginated like any list (R6.1): `per_page` up to `100`, and an MR with more than `100` discussions requires walking pages; a comment set silently cut at a round page boundary is forgotten pagination, not the whole review.
- R9. Batch posting protocol and post-write verification:
- R9.1. verification=manual; Line-anchor validation against diff hunks (trap). The skill documents: a `position` is accepted only on lines inside diff hunks (added or changed lines); `new_line` on a context (unchanged) line is rejected with HTTP `400` and a body naming an invalid line_code; grep finding the marker in the file does not make the line a valid anchor — before posting, collect the new-side line ranges from the hunk headers (`@@ +<start>,<count> @@`) of `GET .../merge_requests/<iid>/diffs` (paginated per R6.1) and check every anchor against them; on a position-rejecting `400` the fallback is the same body without `position` — a top-level note with `<path>:<line>` written into the text so the reference is not lost.
- R9.2. verification=manual; diff_refs freshness. The skill documents: `diff_refs` (`base_sha`/`start_sha`/`head_sha`) change when the author pushes to the source branch or the target branch moves; they are taken from the single-MR endpoint (R8.3) immediately before posting a batch and are never cached across sessions; a long batch can have its shas rotated mid-run; notes created against a superseded diff version are marked outdated by GitLab (Definitions) — expected behavior, not an error.
- R9.3. verification=manual; Batch posting protocol. The skill documents, for posting tens of line-anchored comments in one run: post the first comment alone (a canary) and verify the response schema — discussion id, note id, position — before posting the rest; detect failures by the response body (fields `message`/`error`) and the stderr line, never by the exit code — `glab api` exits `0` on HTTP `400` for POST as well (R2.2); on a `400` naming position/line_code, retry the same body without `position` (R9.1); save `discussion_id`/`note_id` from every POST response so that the final verification is the set of saved ids, not a full re-fetch of all discussions. This direct protocol is the fallback for instances without the draft-notes API and for posting outside the review flow; when the draft-notes API is available, a multi-comment review goes through the draft review flow (R10.1, R10.3).
- R9.4. verification=manual; Mass-posting rate caution (instance-dependent). The skill documents: posting tens of comments in rapid succession under one account has — once, cause unconfirmed — transiently affected that account's web UI; the rule is to work in batches, verify via the API, and warn the user before large insertions.
- R9.5. verification=manual; Post-write verification (instance-dependent). The skill documents: a raw-body POST (`--input`) was once observed answering `rc=0` with `{"message":"500 Internal Server Error"}` in the body while the resource had in fact been created; after mass writes, creation is verified by the response id or a targeted GET — trusting neither the exit code (R2.2) nor the message in the body alone. The mechanized, read-only after-the-fact form of this check is the bundled `mr-verify-posted.sh` (R13.9), previously manual.
- R10. Draft review flow:
- R10.1. verification=manual; Draft review flow (preferred). The skill documents, for posting a review with multiple comments: create N draft notes first, then publish them all with one call — not one public POST per comment. Endpoints: `GET .../merge_requests/<iid>/draft_notes` (the list; doubles as the availability probe — an empty array when there are none), `GET .../draft_notes/<draft_note_id>`, `POST .../draft_notes` (body per R10.2; the response carries `id`, `note`, `position`, `line_code`, `resolve_discussion`, `discussion_id`, `commit_id`, `author_id` — the position is stored verbatim and the `line_code` is computed), `DELETE .../draft_notes/<draft_note_id>`, `PUT .../draft_notes/<draft_note_id>/publish` (single draft; per GitLab docs, not live-verified), `POST .../draft_notes/bulk_publish` (publishes all pending drafts of the current user at once; optional body fields `note` — a summary note added to the MR, `internal`, `reviewer_state` (`requested_changes`|`reviewed`) — per GitLab docs, not live-verified). Before publishing a draft note is visible only to its author (per GitLab docs), so creating, inspecting, and deleting drafts is private and recoverable; publishing is the single public step. The mandatory `[ai] ` prefix (R5.1, invariant R15.1) applies to every draft note. `diff_refs` freshness (R9.2) applies to draft positions: if the shas rotate between creation and publishing, the published notes are marked outdated — expected, not an error. Live-verified on GitLab 18.7.7-ee: list/create/delete and the existence of both publish routes (verified without publishing); the publish actions themselves are per GitLab docs, not live-verified (R14.4).
- R10.2. verification=manual; Draft-note creation contract (traps, live-verified). The skill documents: `note` is a top-level string — a nested object `{"note":{"body":...,"position":...}}` answers HTTP `400` `{"error":"note is invalid"}`; `position` is a top-level sibling of `note` (as are `resolve_discussion` and `in_reply_to_discussion_id` per GitLab docs), built exactly like the discussions position of R8.3 (`diff_refs` from the single-MR endpoint, `position_type` `"text"`, `new_path`+`new_line` or `old_path`+`old_line`); a raw-body POST (`--input`) without a Content-Type header answers HTTP `415` `{"error":"The provided content-type '' is not supported."}` — always pass `-H "Content-Type: application/json"`; the server does NOT validate a draft's anchor at creation — a position with `new_line` beyond the end of the file was accepted, and `old_path` proved optional in practice — therefore line-anchor validation against hunk ranges (R9.1) is performed client-side BEFORE creating the drafts: an invalid anchor surfaces only at publish time, after the batch has gone public; glab 1.36.0 has no high-level draft-note commands (verified against help) — the flow rides on `glab api` only.
- R10.3. verification=manual; Scope of the draft flow and the direct-POST fallback. The skill documents where each posting path applies: the draft flow (R10.1) is the preferred way to post a review with multiple comments; a direct `POST .../discussions` remains correct for a single comment outside a review; replies into existing threads go per R8.5 (the GraphQL fallback; draft notes also accept `in_reply_to_discussion_id` for replies per GitLab docs, not live-verified); if the availability probe (`GET .../draft_notes`) shows the API missing on the instance (`404`), the instance is marked instance-dependent per R14.4 and the review is posted by the direct batch protocol (R9.3).
- R10.4. verification=manual; Draft review order of operations. The skill documents the fixed order: fetch `diff_refs` from the single-MR endpoint (R8.3) → validate every anchor against hunk ranges, client-side (R9.1, R10.2) → create N draft notes, detecting failures by the response body, never the exit code (R2.2, R9.3) → verify the draft set via GET (paginated per R6.1) → one `bulk_publish` → optionally verify the published notes via the discussions endpoint (R8.4, R8.7) — this publish-verification step is mechanized by the bundled `mr-verify-posted.sh` (R13.9). A wrong draft is deleted and recreated before publishing (creation is private); after publishing, the draft list empties.
- R11. Processing incoming review comments as the MR author:
- R11.1. verification=manual; Review comment identification. The skill documents, for processing incoming review comments as the MR author (Definitions: review comment processing): every comment is processed individually, keyed by its note id; grouping comments by topic into one work item is forbidden; two comments count as one work item only when they state the same requirement, not when they share a topic; a doubt about sameness is resolved by treating the comments as separate and, where the intent stays unclear, by asking the comment author or the user.
- R11.2. verification=manual; New-comment selection. The skill documents: selecting "new" comments by a `created_at` threshold is forbidden as the only mechanism, because an approximate threshold silently skips a late-arriving note; each round re-fetches the full discussions list (paginated per R8.7) and reads every non-system note, treating a thread as already handled exactly when it contains the agent's own reply; when a `created_at` threshold is used as an auxiliary filter, it is taken as the maximum id and `created_at` of every previously processed note as recorded from fetched data, never from unrecorded memory.
- R11.3. verification=manual; Resolve discipline. The skill documents: a discussion is resolved only after the code or spec change requested by the comment is pushed, or after a reasoned reply confirming that no change is needed is posted in the thread; a comment phrased as a question is not resolved without the comment author's confirmation or an explicit user decision; resolving several discussions in one batch run without reading the text of each is forbidden; after replies are posted, the remaining unresolved set is re-verified per discussion, never by counting.
- R11.4. verification=manual; Reply instead of change. The skill documents: a reply stating that no change is needed must cite the verified fact it rests on as a file and line reference; when the check proves the agent's earlier interpretation of the comment wrong, the requested change is made rather than argued against.
- R12. gitlab-tools foundations:
- R12.1. verification=manual; Toolkit inventory and location. The skill ships the gitlab-tools toolkit in the `tools/` subdirectory next to SKILL.md: the shared library `lib.sh`, the optional site defaults `config.sh`, the scripts `mr-auth-probe.sh`, `mr-list.sh`, `mr-card.sh`, `mr-updates.sh`, `mr-has-updates.sh`, `mr-diff.sh`, `mr-threads.sh`, `mr-comment.sh`, `mr-draft-review.sh`, `mr-reply.sh`, `mr-resolve.sh`, `mr-verify-report.sh`, `mr-verify-posted.sh` (all executable), the toolkit documentation `README.md`, and `examples/` (sample `comments.json`, `verdicts.json`, and `--expect` inputs, including a bad-prefix sample). The toolkit is location-independent: scripts resolve `lib.sh`/`config.sh` and the default state directory relative to their own location, so it works from any checkout or deployment path. The repository copy is the source of truth; per-script contracts (arguments, exit codes, guards, stdout sections) are documented in `tools/README.md` as part of the toolkit, while the SKILL.md section carries the activation rule and the guard highlights. Runtime state (the default `GITLAB_TOOLS_STATE_DIR`, `<tools>/.state`) is not part of the toolkit and stays out of the repository. The toolkit's built-in defaults carry functional values (the reference instance host); the placeholder rule (R14.3) applies to SKILL.md text, not to the toolkit's configuration defaults and its `README.md`/`examples/` observation records.
- R12.2. verification=manual; Activation rule: tools are the preferred mechanical path. The toolkit's scripts are preferred over hand-built glab calls for exactly their covered operations: a global MR listing by role across all accessible projects (`mr-list.sh`), MR update polling with a state marker (`mr-updates.sh`), the fast boolean has-updates timer check (`mr-has-updates.sh`; also the gate command of the timer/watcher scenario, R13.17), a live token-health probe (`mr-auth-probe.sh`), the MR card (`mr-card.sh`), the true local MR diff with file/stat/hunk/conflict modes (`mr-diff.sh`), thread dumps (`mr-threads.sh`), a single line-anchored comment (`mr-comment.sh`), a batch review via draft notes with safe publish (`mr-draft-review.sh`), replies into existing discussions (`mr-reply.sh`), resolving one thread (`mr-resolve.sh`), the verdict-plan front-end over the two (`mr-verify-report.sh`), and read-only post-publish verification instead of ad-hoc inline scripts (`mr-verify-posted.sh`). Raw glab remains the path for everything the toolkit does not cover — MR/issue/CI operations, project-scoped lists, descriptions, merges — and remains the reference for understanding the underlying API semantics: the toolkit mechanically implements the protocols of R3.2, R1.3, R9.1..R9.3, R8.5, R9.5, R10.1..R10.4, R11.3; it does not replace the knowledge behind them. The skill documents this tools-vs-raw-glab split in its toolkit section.
- R12.3. verification=manual; Shared runtime contract (lib.sh, config.sh). Every script sources `lib.sh`; an optional `config.sh` next to it only fills unset/empty variables, so configuration precedence is: environment > `config.sh` > built-in defaults. Variables: `GITLAB_HOST` (instance host for every call), `GITLAB_DEFAULT_PROJECT` (lets the `<project>` positional be omitted; the remaining positionals shift left), `GITLAB_REPO` (clone used for sha recovery, hunk building, and the local MR diff; default: the clone containing the current directory; a per-run `--repo <dir>` flag overrides it — R12.4), `GITLAB_COMMENT_PREFIX` (the configured comment prefix checked on every write; default `[ai] ` — R12.5), `GITLAB_TOOLS_STATE_DIR` (default `<tools>/.state`, created on demand; bare `--state` filenames resolve under it), plus the per-run sha overrides `GT_BASE_SHA`/`GT_START_SHA`/`GT_HEAD_SHA` and `GT_LSREMOTE=0` (disables the network step of sha recovery). Exit codes across the toolkit: `0` success, `1` failure, `2` usage error (the boolean `mr-has-updates.sh` — R13.11 — redefines the `0`/`1` pair as updates-present/no-updates and adds `3` for an API/network failure); output is plain text without ANSI colors. The `glab api` exit-`0`-on-HTTP-error trap (R2.2) is neutralized centrally — failures are detected from the stderr HTTP line and error-shaped bodies (`gt_api`/`gt_get`/`gt_body_is_error`) — and pagination always runs `per_page=100` + `--paginate` with concatenated page arrays parsed by repeated `raw_decode` (R6.1).
- R12.4. verification=manual; `--repo <dir>` unification. Every toolkit script accepts the optional `[--repo <dir>]` flag with identical semantics — except `mr-auth-probe.sh`, which takes no clone-related flags (R13.12: its only optional argument is the `[host]` positional) — and the seven scripts that lacked it (`mr-list.sh`, `mr-updates.sh`, `mr-has-updates.sh`, `mr-threads.sh`, `mr-reply.sh`, `mr-resolve.sh`, `mr-verify-posted.sh`) join `mr-comment.sh`, `mr-draft-review.sh`, `mr-verify-report.sh`, and the new scripts carry it per their contracts (R13.13, R13.15). Semantics everywhere: `--repo <dir>` overrides `GITLAB_REPO` for the invocation — precedence flag > environment > `config.sh` > built-in default (R12.3, with environment > `config.sh` preserved); a `--repo` naming a nonexistent directory is a usage error (exit `2`). For scripts that make no clone use of the value the flag is accepted for interface uniformity and validated the same way (the precedent defect: `mr-has-updates.sh --repo <dir>` exited `2` as an unknown option). The usage text printed on a usage error by every script accepting `--repo` includes the hint line `clone is configured via GITLAB_REPO env or config.sh`.
- R12.5. verification=manual; Configurable comment prefix (`GITLAB_COMMENT_PREFIX`). New configuration variable `GITLAB_COMMENT_PREFIX` resolved per the shared precedence — environment > `config.sh` > built-in default `[ai] ` (Definitions: configured comment prefix; an unset variable keeps the built-in default, behaving byte-identically to a run with the default set explicitly). Every body-writing path checks or normalizes against the configured prefix: `mr-comment.sh`, `mr-reply.sh`, and `mr-draft-review.sh` (draft bodies and reply items, the `--publish` path included) refuse a body not starting with it, and `--no-prefix` remains the only explicit opt-out posting the body as-is — invariant R15.6 carried over verbatim from the fixed prefix to the configured one; `mr-verify-report.sh` adds the configured prefix to a `text` without it and never doubles one already present. The selection filters narrow by the configured prefix: `mr-verify-posted.sh --ai-only` (both the `--expect` candidates and the `--max-note-id` baseline) and `mr-threads.sh --ai-only` select notes starting with it (both previously hardcoded the fixed prefix). The prefix rule itself (R5.1, invariant R15.1) keeps its strength unchanged — every machine-generated comment carries the marker, without exceptions; the variable only lets the MR/repository owner prescribe the marker text (observed: an owner required `[ai] ` on their MR — the value the built-in default was later set to). Implementation must synchronize: SKILL.md `§9` (the prefix rule — the marker text is configurable, the default `[ai] `), the SKILL.md `§22` configuration paragraph and the frontmatter `description` (R14.7), `tools/README.md` (the Configuration table row, trap `8`, and every per-script mention of the prefix), and `tools/config.sh` (the documented variable and its commented default).
- R13. Toolkit script contracts:
- R13.1. verification=manual; mr-updates.sh contract. `mr-updates.sh <project> <mr_iid> [--since <iso8601|sha>] [--state <file>] [--fetch]` prints the stdout sections: `== MR state ==` (title, state, draft, updated_at, branches, recovered head sha with its provenance), `== commits (new since) ==` (inside a clone: `git log origin/<source> --not origin/<target>` with a per-commit diffstat suffix; otherwise the API commits endpoint), `== notes (new since) ==` (notes newer than the marker, newest first), and — only when the delta contains resolution events — `== thread status changes ==` (system notes `[resolved]`/`[unresolved]`/`resolved all threads` mapped to the discussion id by note id via a lazy discussions GET, with the thread anchor, who flipped the state, and the first line of the original note; an unattached `resolved all threads` note is reported as an MR-timeline note). `--since` accepts an ISO8601 timestamp or a commit sha (the walk stops right before it); when a `--state` marker exists, `--since` is ignored for the delta with a NOTE. With `--state <file>`: after printing, the head sha (+ its `short_id`) and the max note id/created_at are stored; the next run reports only the delta; no marker file means a full dump. The marker schema is additive (`"schema": 2`): older markers load unchanged, a masked sha (`__SECRET_N__`) stored by an older run is ignored for the cutoff (the timestamp cutoff takes over), and a masked sha is never written as a cutoff. `--fetch` refreshes `origin/<source_branch>` first — the only local write, opt-in; everything else is GET-only.
- R13.2. verification=manual; mr-threads.sh contract. `mr-threads.sh <project> <mr_iid> [--open|--all] [--ai-only] [--max-chars N] [--full]` dumps discussions as readable text: discussion id, resolved state (resolved iff every non-system note has `resolved: true` — the instance-independent rule of R8.6), anchor `path:line` (new side; old side when there is no new line; a range for multi-line anchors), authors, and note bodies truncated to `thread-truncate-default-chars` characters by default (`--max-chars N`, `--full`); a trailing count line reports how many of the total discussions were shown. `--open` (default) keeps unresolved threads only; `--ai-only` keeps threads containing a note that starts with the configured prefix (default `[ai] `). GET-only: no writes, no clone required; exit codes per the shared contract (R12.3).
- R13.3. verification=manual; mr-comment.sh contract. `mr-comment.sh <project> <mr_iid> <path> <line> <body-or-@file> [--old-side] [--no-prefix] [--force] [--dry-run] [--repo <dir>]` posts ONE line-anchored comment: it reads `diff_refs` from the single-MR endpoint, recovers real shas (the masked-sha ladder of R13.8; dies with a clear message when masking meets no usable clone), validates `<line>` against locally built hunk ranges for `<path>`, and refuses with the list of valid ranges when the anchor is outside a hunk (`out-of-hunk`) or the path is not part of the diff (`not-in-diff`) — unless `--force` posts unpositioned with `path:line` prepended to the body (after the `[ai] ` prefix when present); without a clone the comment is posted unpositioned with the same prepend and a NOTE. The POST goes to the discussions API and creation is verified by a follow-up GET (never by the POST response — the `500`-in-body trap); success prints `posted + verified: discussion <id>, note <id>, anchor <path>:line`. `--dry-run` prints the exact payload (including `position`) without posting. The prefix refusal and the `--no-prefix` escape follow invariant R15.6; the anchor-validation protocol is that of R9.1 with locally built hunks.
- R13.4. verification=manual; mr-draft-review.sh contract. `mr-draft-review.sh <project> <mr_iid> <comments.json> [--publish] [--dry-run] [--no-prefix] [--repo <dir>] [--ignore-stray]` is the batch review flow over the draft-notes API (R10.1..R10.4). `comments.json` is a non-empty JSON array of draft items `{"path", "line", "body", "old_side"?}` and/or reply items `{"reply_to_discussion_id", "body"}`; a reply item must not carry `path`/`line`; input validation failures list every bad entry and abort before any write. Pipeline: parse and prefix-check → resolve shas and build hunk ranges locally for every unique draft path (reply-only batches need no shas and work without a clone) → print the validation table (`ok` / `will-post-unpositioned` / `cannot-validate (no clone)`) → check that every reply target discussion exists (GET) → the stray-draft guard → create drafts on `draft_notes` (top-level `note` + `position`, Content-Type header per R10.2) → verify the drafts via GET → post reply items immediately through `mr-reply.sh` (replies cannot wait in the draft box; they are real posts even without `--publish`, announced loudly) → optionally publish. Stray-draft guard (Definitions; invariant R15.6): before creating anything, the pending `draft_notes` of the current user are listed; any pre-existing drafts refuse the run with the ids and the deletion command (delete them first, or pass `--ignore-stray` to accept the risk); a dry run only warns. `--publish` publishes ONLY the drafts created by this run, one by one via `PUT .../draft_notes/<id>/publish`, each verified by GET (the draft is gone from `draft_notes` and a thread with the same body is found in `discussions`); if the single-publish route answers `404`/`400`, the script prints an explicit warning that `bulk_publish` sweeps ALL pending drafts of the user on the MR and only then falls back to it. Without `--publish` the created draft ids are printed (each deletable by id). `--dry-run` validates and prints payloads with no writes at all.
- R13.5. verification=manual; mr-reply.sh contract. `mr-reply.sh <project> <mr_iid> <discussion_id> <body-or-@file> [--no-prefix] [--dry-run]` replies into an existing thread: the target discussion is fetched first (existence guard; its state and last notes are echoed to stderr for orientation), then the documented REST route `POST .../discussions/<id>/notes` is tried and the reply is verified to sit INSIDE the discussion by GET; on `404`, a failed answer, or the silent-orphan result (the note landed outside the discussion — the `in_reply_to_discussion_id` trap of R8.5), the script falls back to GraphQL `createNote` (MR global id via `project(fullPath).mergeRequest(iid).id`; `discussionId` `gid://gitlab/Discussion/<id>`) and verifies again through REST. Success prints `replied + verified via REST|GraphQL: discussion <id>, note <id>`. `--dry-run` prints both payloads (REST and the GraphQL fallback) and posts nothing. The mandatory prefix and `--no-prefix` follow invariant R15.6.
- R13.6. verification=manual; mr-resolve.sh contract. `mr-resolve.sh <project> <mr_iid> <discussion_id> [--unresolve] [--dry-run]` resolves (or with `--unresolve` unresolves) exactly ONE thread via `PUT .../discussions/<discussion_id>?resolved=true|false`. Guards, all decided by GET before any write: the discussion must exist (a missing id refuses with nothing changed); the thread must contain resolvable notes (system-only or non-resolvable discussions are refused); already being in the requested state is an idempotent OK message with nothing sent. The PUT response is never trusted (the `500`-in-body trap applies to PUT as well): the new state is verified by a follow-up GET. `--dry-run` prints the current state (anchor, first note line, resolvable count) and the exact request without sending anything. No batch mode exists by design — one call resolves one thread so a mistake cannot scale (invariant R15.6); this mechanically implements the resolve discipline of R11.3. The prefix rule (R5.1) is not applicable here: no comment bodies are written.
- R13.7. verification=manual; mr-verify-report.sh contract. `mr-verify-report.sh <project> <mr_iid> <verdicts.json> [--emit <out.json>] [--post] [--yes] [--repo <dir>]` turns a reviewer verdict list into replies and drafts. `verdicts.json` is a JSON array of `{"action": "acknowledge"|"contest", "thread_hint", "text"}` — the target thread is located by `thread_hint`, a substring of the agent's own `[ai] `-prefixed note text; zero or several matching discussions is an error with the candidates listed, the plan is never built on a guess — and `{"action": "new", "path", "line", "old_side"?, "text"}`, the anchor validated like mr-comment.sh (out-of-diff/out-of-hunk items abort with the valid ranges and nothing is written). `text` is the body WITHOUT the prefix — the script adds it, and a text already carrying it is not doubled. The full plan (target discussion, matched note, final body per item) is always printed before any write. `--emit <out.json>` writes a batch file for `mr-draft-review.sh` (replies encoded as `{"reply_to_discussion_id", "body"}`) and performs no MR writes; otherwise posting requires `--yes` (without it only the plan is printed): replies go through `mr-reply.sh`, `new` items through the `draft_notes` flow of `mr-draft-review.sh`. This tool never publishes: created drafts stay private, publish is a separate `mr-draft-review.sh --publish` run (it passes `--ignore-stray` deliberately — it never publishes, so stale drafts are harmless from here).
- R13.8. verification=manual; Instance traps the toolkit encapsulates. The scripts encode the reference-instance traps so callers do not re-hit them: (a) `glab api` exits `0` on HTTP errors — detected from the stderr HTTP line and error-shaped bodies, including the fake `{"message":"500 Internal Server Error"}` body on writes (R2.2, R9.5): every write path verifies by follow-up GET; (b) `40-hex` shas arrive masked as `__SECRET_N__` (REST and GraphQL, flaky per response; the commit `short_id` always survives) — real shas are recovered through the ladder: commits-endpoint `id` when unmasked → `short_id` resolved locally with `git rev-parse` → `git ls-remote origin <source_branch>` (fresh, never masked, writes nothing to the clone) → local `origin/<branch>`/`<branch>` refs; the merge-base comes from `git merge-base` against the target branch (fallback `origin/main`/`origin/master`), and `start_sha` is sent equal to the merge-base; without a usable clone the scripts fail with a clear message; (c) the `/diffs` endpoint returns most files with `collapsed: true` and an empty diff — hunk ranges are built locally with `git diff --unified=0 <merge-base>..<head> -- <path>`, and the true MR diff runs from the merge-base, not from `diff_refs.start_sha` (on the reference instance `start_sha` is the target-branch tip); when the clone lacks the true MR head, validation falls back to the local source-branch tip with a loud warning; (d) the REST reply route may `404` while `in_reply_to_discussion_id` is silently ignored (R8.5) — `mr-reply.sh` verifies the reply landed inside the discussion and falls back to GraphQL `createNote`; (e) anchors are accepted only on lines inside diff hunks (R9.1) — validated locally before any positioned post. The skill text keeps documenting these traps for raw glab usage; the toolkit is their mechanical enforcement.
- R13.9. verification=manual; mr-verify-posted.sh contract. `mr-verify-posted.sh <project> <mr_iid> [--expect <expected.json>] [--drafts] [--max-note-id] [--ai-only] [--max-chars N] [--full]` is the read-only (GET-only; no POST/PUT/DELETE is ever sent) post-publish verifier — the mechanical form of the post-write verification of R9.5 and the publish-verification step of R10.4, used instead of ad-hoc inline scripts after e.g. a `mr-draft-review.sh --publish` run plus raw timeline notes. `--drafts` prints the pending `draft_notes` count of the user plus ids (the pre-existing-draft check before a batch run); `--max-note-id` prints the highest note id on the MR (the marker/baseline for follow-up posts, same basis as the `mr-updates.sh --state` marker — with the caveat that the max here is computed over the single newest page, `sort=desc` with `per_page=100`, so it can diverge from the mr-updates full-list basis only if more than `100` notes share one `created_at`). `--expect <expected.json>` verifies expected posted comments against the discussions listing (paginated per R6.1/R8.7): the file uses the `mr-draft-review.sh` comments.json schema — `{"path", "line", "body", "old_side"?}` anchored items (match = body byte-equality AND position `new_path`/`new_line` — or `old_path`/`old_line` — equality), `{"body"}` unanchored items (body byte-equality anywhere on the MR), and `{"reply_to_discussion_id", "body"}` reply items (body byte-equality inside that discussion); a body starting with `@` names a file read verbatim, the trailing newline included (the `@file` convention of mr-comment.sh/mr-reply.sh; `@-` is not supported); no prefix is forced — expected bodies are the FINAL posted bodies compared byte-exactly as given (an out-of-hunk batch item carries the `path:line` prepend of `mr-draft-review.sh`); `--ai-only` narrows both the `--expect` candidates and the `--max-note-id` baseline to `[ai] `-prefixed notes (the configured prefix). Verdicts per item — `ok` (byte-equal body at the required place), `anchor-mismatch` (the exact body exists but is anchored differently), `body-mismatch` (the expected place exists — an anchor is occupied, the discussion exists, or the body exists elsewhere on the MR — but body and place never coincide; catches the orphan-reply trap of R8.5), `not-found` (neither the body nor the expected place found) — each verdict line carrying the discussion id, note id, anchor, and the matched note's own resolved flag (the script never aggregates thread state; on this instance thread resolved == every non-system note resolved, R8.6). Exit `0` when all expected items are `ok` (informational-only runs included); `1` on failure (a mismatched expected item, unparsable input, an HTTP error; unknown option and bad flag value also exit `1`); `2` usage error — missing arguments or nothing to do, an empty expect array included (shared contract R12.3).
- R13.10. verification=manual; mr-list.sh contract. `mr-list.sh [--role reviewer|author|assignee] [--state opened|closed|merged|all] [--draft|--no-draft] [--json] [--project <group/proj>] [--max N]` lists merge requests by role across all accessible projects — the default `--role reviewer --state opened` is the "which MRs await my review" scenario. It queries the global `merge_requests` endpoint for the CURRENT user (the username of the role filter comes from a live `glab api user` call) with the mandatory `scope=all` (R3.2: the trap is encapsulated so a caller cannot forget it) and full pagination — `per_page=100` plus `--paginate` with concatenated page arrays parsed by repeated `raw_decode` (R6.1, R12.3). The text output prints one block per MR — `references.full`, a `[DRAFT]` mark, the `updated_at` date, `author.username` on the header line, then `title`, `web_url`, and the branch line `source_branch -> target_branch` — sorted by `updated_at` descending with a trailing count line summarizing the query; `--draft`/`--no-draft` filter drafts (`work_in_progress` or a `Draft:`/`WIP:` title prefix), `--project` narrows to one project (exact match on the project path of `references.full` — the global endpoint returns no `project` object; default: all accessible projects), `--max N` caps the list after sorting; `--json` prints the same normalized set as a JSON array, deduplicated by MR id and sorted identically, with the count line on stderr. GET-only: no writes and no clone needed; an empty result of a correct query is a success (exit `0`) printed as an informational line; exit codes per the shared contract (R12.3), with every argument-level error — a bad `--role`/`--state`/`--max` value or an unknown option — exiting `2`.
- R13.11. verification=manual; mr-has-updates.sh contract. `mr-has-updates.sh <project> <mr_iid> [--state <file>] [--no-ci]` is the read-only (GET-only; nothing is ever posted) and clone-free boolean "does this MR have any updates?" check for timers — the caller wakes an agent only when something changed. It compares the current snapshot with its own has-updates marker (Definitions) and prints one human-readable summary line per changed category: commits (a new head short id; the commit walk stops at the marker head, and only short ids are ever stored), notes (any note id above the marker max, system notes included; the notes listing is walked with full pagination so the max note id is exact), threads (resolve/unresolve flips detected from system notes plus the unresolved-note-id set diff, and new discussion ids), MR state and draft/WIP, title and description (length + sha256-prefix hashes; no text stored), reviewers and approved_by username sets (approved_by via the approvals endpoint), merge_status/detailed_merge_status, and the CI pipeline for the current head (`pipelines?sha=<head_sha>` — the sha filter needs the full `40-hex` id, a short id returns an empty list on the reference instance; when the commits endpoint masks the id, the fallback is the newest pipeline of the `refs/merge-requests/<iid>/head` ref), reported on its id/status change. Exit codes redefine the toolkit's `0`/`1` pair (R12.3): `0` — updates present (stdout carries the summary lines, attachable to the timer wakeup); `1` — no updates, and also the first run, which writes a baseline, prints `baseline recorded (...)`, and exits `1`; `2` — usage error; `3` — API/network failure with stderr diagnostics, the marker left untouched so the delta is not lost (the glab `rc=0`-on-HTTP-error trap is neutralized via the lib.sh body/stderr detection; an unreadable marker also exits `3` rather than being silently rewritten). The marker: `--state` is optional, default `<tools>/.state/has-updates/<project-without-slashes>__<iid>.json`; a bare `--state` filename resolves under `GITLAB_TOOLS_STATE_DIR/has-updates/`; the directory is created on demand; the schema is additive (`"schema": 3`), holds no secrets and no full `40-hex` shas, is written atomically (tmp + rename), and is rewritten only on a baseline or a detected change — an unchanged run never touches it. API budget: about six GETs — the single-MR endpoint, commits, notes (paginated), discussions (one `per_page=100` page, newest first: new-thread detection needs the fresh tail, while resolve flips of old threads are caught from system notes), approvals, pipelines. `--no-ci` excludes the CI category entirely — the CI pipeline for the current head is not requested (the sha-filter pipelines GET and its ref-pipeline fallback are both skipped; one GET saved from the about-six API budget), is not compared against the marker, and no CI line appears in the stdout summary; every other category works unchanged. The marker structure does not change (`"schema": 4` per R13.14; no new fields): under `--no-ci` the stored pipeline fields are not refreshed and keep their last saved values (a first-run baseline under `--no-ci` stores no pipeline fields — the additive absent-field semantics of R13.14). A CI change that happened during a `--no-ci` window is therefore detected by the next run without `--no-ci` — the current pipeline compared against the stale saved value — so the boolean "something changed" meaning is preserved and the CI delta is not lost. Exit codes are unchanged (`0`/`1`/`2`/`3` above); the flag does not affect the first-run baseline semantics — the first run still records a baseline, prints `baseline recorded (...)`, and exits `1`.
- R13.12. verification=manual; mr-auth-probe.sh contract. `mr-auth-probe.sh [host]` is the live token-health check — the mechanical form of the live-probe rule of R1.3 (the `glab auth status` output is a hint, never a verdict; only a live call decides). It performs exactly one API call — GET `user` — through the gt_api machinery of lib.sh, so the glab `rc=0`-on-HTTP-error trap (R2.2, R12.3) is neutralized centrally. The optional `[host]` positional selects the target host for this invocation; when omitted, the host resolves per the shared runtime contract (R12.3: `GITLAB_HOST` environment > `config.sh` > built-in default). Exit codes: `0` — the call answered `200` and stdout carries exactly `ok <username>` (the `username` field of the response); `1` — the probe failed (an HTTP error, `401` first of all, or a network failure), with a stderr diagnostic line naming the host and the HTTP code (or the network error); `2` — usage error (R12.3). GET-only: no writes, no clone, no state files; token values are never read, echoed, or stored (R1.2). At implementation the skill's authorization and multi-host sections (SKILL.md `§2`, `§15`) reference it as the preferred mechanical probe in place of the raw `glab api user --hostname <host>` call.
- R13.13. verification=manual; mr-card.sh contract. `mr-card.sh <project> <mr_iid> [--json] [--full] [--repo <dir>]` prints the MR card — the mechanical form of the "view one MR" step of the watcher loop (raw `glab mr view` remains the interactive project-scoped path). Fields, from the single-MR endpoint plus the approvals endpoint: title with a `[DRAFT]` mark (R3.4), state, `work_in_progress`, author username, reviewer usernames, approved_by usernames (the approvals endpoint, the same basis as R13.11), `approved` (boolean) and `approvals_required` (number or null, both from the approvals endpoint), `blocking_discussions_resolved` (R8.6), `detailed_merge_status` and the legacy `merge_status`, source and target branches, the recovered head sha with its provenance (the masked-sha ladder of R13.8 — the API sha arrives masked on the reference instance), `changes_count`, and the description truncated to `thread-truncate-default-chars` characters by default (`--full` prints it whole — the truncation convention of R13.2); plus the local diffstat of `<merge-base>..<head>` (merge-base per R13.8). Text output is one labeled block modeled on the mr-list.sh block style (R13.10); `--json` prints one normalized JSON object with the same fields — `diffstat` as an object of `files`/`insertions`/`deletions`, the description under the same truncation flags — and the no-clone NOTE goes to stderr so stdout stays parseable (the count-line-on-stderr pattern of R13.10). Without a clone the card is still printed, without the diffstat, with an explicit NOTE saying so (the degrade-and-say-so pattern of R13.3). GET-only plus read-only clone use — nothing is fetched or written; exit codes per the shared contract (R12.3); a missing project/MR exits `1` with the HTTP diagnostics on stderr.
- R13.14. verification=manual; Merge-status polling category (mr-updates.sh, mr-has-updates.sh). Both polling scripts cover a merge-status category — `detailed_merge_status`, the legacy `merge_status`, `blocking_discussions_resolved` (R8.6), and the approvals username set — reported with the existing one-line-per-category discipline. `mr-has-updates.sh` (R13.11) extends its existing merge status category with `blocking_discussions_resolved` flips (`detailed_merge_status`, `merge_status`, and approvals are already tracked there); its marker schema becomes `"schema": 4` (superseding the `"schema": 3` of R13.11; the additive rule of invariant R15.7 is unchanged). `mr-updates.sh` (R13.1) gains a `== merge status ==` stdout section, printed only when the delta contains a change in these fields — one line per changed aspect (detailed/legacy status transitions, the blocking flag flip, approvals +username/-username diffs) — and with `--state` its marker additionally stores the merge-status snapshot and the approvals set; the marker schema becomes `"schema": 3` (superseding the `"schema": 2` of R13.1; additive rule unchanged). Marker additivity in both: markers written by older versions load unchanged; a new field absent from an older marker counts as «not changed» on the first read after the upgrade — the new category never reports a false change merely because an old marker lacks the field — and the new fields are written on the next store; the no-secrets discipline of R13.11 carries over to the stored approvals set (usernames only).
- R13.15. verification=manual; mr-diff.sh contract. `mr-diff.sh <project> <mr_iid> [--files|--stat|--hunks|--conflicts] [--repo <dir>]` computes the true local MR diff as a first-class mechanical operation — the diff traps of R13.8(c)/(e) (the collapsed `/diffs` endpoint, the merge-base rule) made operational. A usable clone is required; without one the script exits `1` with a clear message. Construction: shas are recovered through the ladder of R13.8, and the diff always runs `<merge-base>..<head>` with the merge-base from `git merge-base` against the target branch (fallback `origin/main`/`origin/master`) — never from `diff_refs.start_sha` (on the reference instance it is the target-branch tip) and never as a two-dot `git diff origin/<target>..<head>` (a target that moved ahead unfolds other authors' commits). Clone-freshness guard: when the clone lacks the true MR head, every mode prints a loud warning naming the expected head and the fallback tip and degrades to the local source-branch tip — the established fallback of R13.8(c); a `--conflicts` verdict computed from the fallback head is labeled as such. Modes: default — the full unified diff `<merge-base>..<head>`; `--files` — one line per changed path with its status: `new`, `deleted`, `renamed <old> -> <new>`, `modified`; `--stat` — the diffstat (files, insertions, deletions); `--hunks` — the machine-readable new-side hunk ranges per file, one line per changed file, `<path>\t<start>-<end> <start>-<end> ...` (a path with no new side carries `-` in place of ranges) — the anchor-validation source of truth of R9.1; `--conflicts` — a write-free local merge simulation with `git merge-tree` semantics between the target-branch tip and the MR head: exit `0` — the merge is clean, exit `1` — conflicts, with the list of conflicting paths on stdout. Exit codes: standard `0`/`1`/`2` (R12.3) for all modes except `--conflicts`, which owns the `0`/`1` pair as its verdict (`0` clean, `1` conflicts); a `--conflicts` check that could not be performed at all (no usable clone or head, a git failure) exits `3` with stderr diagnostics — the outcome/failure separation of R13.11; usage errors exit `2` in every mode. Single source of truth for hunks: the hunk-range construction exposed by `--hunks` is ONE shared construction (lib.sh level); `mr-comment.sh` and `mr-draft-review.sh` must validate anchors against exactly this construction — duplicating the hunk internals per script is forbidden (internal refactoring beyond this duty is not constrained by the spec). GET-only plus read-only clone use; nothing is fetched or written.
- R13.16. verification=manual; mr-threads.sh `--no-system`. `mr-threads.sh <project> <mr_iid> [--open|--all] [--ai-only] [--no-system] [--max-chars N] [--full]`: the `--no-system` flag drops notes with `system: true` from the dump, and a thread consisting only of system notes is not printed at all; the trailing count line keeps its meaning (how many of the total discussions were shown — under `--no-system` the system-only threads drop out of the shown count); the resolved state of a printed thread is still computed over its non-system notes (the instance-independent rule of R8.6). Motivation (observed during review processing): CI-bot progress comments (system notes) clutter the dump and bury the human review threads. GET-only, no clone; exit codes per the shared contract (R12.3).
- R13.17. verification=manual; Timer/watcher scenario (SKILL.md `§22`). The toolkit section of SKILL.md (`§22`) must carry the timer/watcher recipe — `mr-has-updates.sh <project> <mr_iid> --state <file>` as the scheduler's gate command: exit `0` (updates present) — the fire happens, and the stdout summary lines are attached to the wakeup message; exit `1` (no updates; also the baseline first run) — the fire is skipped, the baseline recording being the intended arming step, not an error; exit `3` (API/network failure) — the marker is untouched, the fire is skipped without an alert, and the check is retried on the next tick (the delta is never lost — R13.11). The recipe is written generically for any scheduler that fires when its gate command exits `0`, and its setup template must: pass an explicit `--state <file>` (the watcher owns its marker file), set `GITLAB_REPO` to the clone the woken agent will use for diff/anchor work (the gate command itself is clone-free), and show the full lifecycle — the first tick records the baseline (`baseline recorded (...)`, exit `1`, no fire) and every later tick fires only on a real delta. A watcher that does not care about CI events passes `--no-ci` in its gate command, and the setup template mentions the flag (R13.11). Implementation adds the recipe to `§22` and grows the frontmatter `description` accordingly (R14.7).

- R15.3. verification=manual; The iid≠id rule (R3.3) with the `404`-wrong-project heuristic is inviolable.
- R15.4. verification=manual; Revision monotonicity: a revision may extend or refine existing content but must not silently weaken or remove any rule present in the previous version; a refinement that corrects a verified inaccuracy (for example, sharpening the scope=all effect from "empty list" to "only the caller's own MRs") is allowed when the correction itself passes the accuracy gate.
- R15.5. verification=manual; The accuracy gate (R14.1..R14.4) and the placeholder rule (R14.3) apply to every revision, including inherited examples and invariants: content may not be kept on recollection alone.
- R15.6. verification=manual; Toolkit safety invariants. The gitlab-tools scripts mechanically enforce, and no revision may weaken: the `[ai] ` prefix (R5.1, R15.1) is checked before every write that posts a body — `--no-prefix` is the only explicit escape; anchors are validated against locally built hunk ranges before any positioned post — `mr-comment.sh --force` and the no-clone path post unpositioned with `path:line` prepended, never a blind positioned POST; the stray-draft refusal — creating drafts over pre-existing pending drafts is refused unless `--ignore-stray` accepts the risk; single-id publish — `mr-draft-review.sh --publish` publishes only the drafts created by the current run, with the `bulk_publish` fallback gated behind an explicit all-drafts warning; and single-thread resolve — no batch resolve mode exists, by design (R11.3).
- R15.7. verification=manual; Configuration and marker stability. The configuration precedence `environment > config.sh > built-in defaults` (R12.3) and the additive evolution of the state-marker schema (R13.1: new fields may be added, older markers must keep loading, masked shas are never stored as cutoffs) are stable contracts: a revision may extend them but must not reorder the precedence or break older markers. The has-updates marker of R13.11 follows the same additive rule (schema `3`) and the same no-secrets discipline (no full `40-hex` shas, no MR text).

## Usage constraints

- The skill is instructions for operating glab; it is not a GitLab API reference: endpoints appear only as far as the covered workflows need them.
- The skill does not handle secrets: token values never appear in the skill or in command lines in examples; login reads the token from standard input or the environment.
- The `[ai] ` prefix is an honesty marker for machine-generated comments, not a style preference; it applies to every posted comment without exception (R15.1), and the toolkit refuses writes without it (R15.6).
- The gitlab-tools scripts are the preferred mechanical path for exactly their covered operations; raw glab remains the path for everything else and the reference for the underlying API semantics (R12.2).
- glab flags are version-dependent: on any version other than the one recorded in the skill, re-verify via `--help` before relying on a flag or default (R14.2).

## Error handling

- A divergence between the skill and this specification is either a spec gap (fix the spec) or a skill bug (fix SKILL.md); silent tolerance is forbidden. The same rule covers the toolkit: a divergence between a gitlab-tools script and its contract (R12, R13, R15.6, R15.7) is either a spec gap (fix the spec) or a tool bug (fix the script or `tools/README.md`).
- An unverifiable flag or claim discovered in the skill is removed or explicitly marked version/instance-dependent (R14.4); removal of content carrying an invariant is forbidden — re-verify instead (R15.1..R15.3, R15.5).
- A glab version change triggers a re-verification pass over all flags, defaults, and behavioral claims (R14.2, R15.5); the version stamp in the skill intro is updated accordingly.

## Dependencies

- None on other skills. Assumes a bash environment with glab installed and at least one authenticated host. The gitlab-tools toolkit additionally needs `python3`, and for sha recovery and hunk validation a git clone of the project (`--repo <dir>`, `GITLAB_REPO`, or run from inside the clone); without a clone the read-only scripts still work, while anchored writes degrade to unpositioned posts (R12.3, R13.3, R13.8); `mr-diff.sh` additionally requires a clone outright (R13.15).
