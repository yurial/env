# Скилл `spec`

Status: stable
Spec source of truth for: скилл OpenCode `spec` — авторинг проектных спецификаций, spec-first flow и механические проверки спек

## Overview

Скилл `spec` задаёт процесс создания и ревью проектных спецификаций, согласования связанных контрактов, проверки соответствия кода спекам и реализации по утверждённым требованиям. Механическую часть проверок формата выполняет `speclint.py`; содержательные свойства проверяются семантическим проходом и ревью.

## Scope

**In:** авторинг и ревью проектных спецификаций; spec-first изменения поведения; проверка связанных спек; механические и семантические проверки; планирование, реализация и проверка изменений по утверждённой спеке.

**Out (non-goals):** README и общая документация проекта; формальные TLA+-спеки, TLC-модели и доказательства; самостоятельное разрешение содержательных конфликтов между спеками.

## Definitions

- `spec/spec-first` — процесс, в котором управляющая спека обновляется и проверяется до начала реализации изменения поведения.
- `spec/reference-id` — стабильный идентификатор спеки из `specs/index.md` либо имя компонента в заголовке спеки малого проекта без индекса.
- `spec/open-deviation` — подтверждённое расхождение между действующей спекой и кодом, которое ещё не устранено.

## Interface

- `speclint.py <path>...` — запускает механическую проверку одного или нескольких Markdown-файлов либо директорий.
- `path` — путь к Markdown-файлу или директории.
- Допустимые статусы спеки и индекса: `draft`, `stable`.
- Допустимые семейства prefixed-записей: `R`, `E`, `I`, `V`, `T`, `J`; записи отклонений используют `D-ID`.

## Configuration

- `root-spec-growth-guide`: integer; approximately 300 lines; fixed; ориентир для предложения перенести корневую `SPEC.md` в дерево `specs/`; связан с R2.3.
- `speclint-clean-exit-code`: integer; 0; fixed; код выхода при отсутствии находок; связан с R6.5.
- `speclint-warning-exit-code`: integer; 1; fixed; код выхода при предупреждениях без ошибок; связан с R6.5.
- `speclint-error-exit-code`: integer; 2; fixed; код выхода при ошибках линта или неверном вызове; связан с R6.1 и R6.5.
- `task-file-count-decomposition-guide`: integer; approximately 5 files; fixed; ориентир для рассмотрения дополнительной декомпозиции задачи; связан с R8.7.

## Requirements

- R1. Общие правила применения и управления изменениями:
- R1.1. verification=manual; Скилл применяется при создании, изменении или ревью `SPEC.md`, `specs/<component>.md`, `specs/index.md`, `specs/GLOSSARY.md` и colocated `SPEC.md` библиотеки.
- R1.2. verification=scenario; Запрос на изменение функциональности, поведения, интерфейса или ограничений запускает spec-first flow до реализации.
- R1.3. verification=manual; Скилл применяется при проверке связанных спек на конфликты и дрейф контрактов, а также при реализации кода по существующей спеке.
- R1.4. verification=manual; Агент не использует скилл для README, общей документации, формальных TLA+-спек, TLC-моделей или доказательств.
- R1.5. verification=manual; До редактирования файлов агент классифицирует запрос как изменение поведения, ревью спеки, реализацию по существующей спеке, небольшое однозначное изменение либо новую инициативу с несколькими независимо проверяемыми возможностями.
- R1.6. verification=manual; Агент не представляет неподтверждённое допущение как факт.
- R1.7. verification=manual; Агент приостанавливает затронутое решение, если неизвестное влияет на публичный интерфейс, безопасность, совместимость, сохранность данных или архитектурные границы.
- R1.8. verification=manual; Содержательный конфликт нормативных требований связанных спек приостанавливает затронутую работу до решения пользователя.
- R1.9. verification=manual; Ревью спеки не изменяет код и не переписывает нормативные решения пользователя без отдельного запроса.
- R1.10. verification=manual; Реализация по существующей спеке начинается только после подтверждения, что спека покрывает задачу.
- R1.11. verification=manual; При пробеле в контракте агент обновляет спеку либо запрашивает решение пользователя и не импровизирует молча.
- R1.12. verification=manual; Агент сообщает о непроведённых проверках отдельно и не объявляет полное соответствие, если обязательные проверки не выполнены или известные расхождения остаются открытыми.

- R2. Размещение и жизненный цикл спек:
- R2.1. verification=manual; Малый проект использует корневую `SPEC.md`.
- R2.2. verification=manual; Проект с несколькими компонентами использует `specs/<component-or-feature>.md` и единый `specs/index.md`.
- R2.3. verification=manual; При появлении второй компонентной границы или росте корневой спеки примерно до `root-spec-growth-guide` агент предлагает перейти к дереву `specs/` без дублирования содержимого.
- R2.4. verification=manual; Независимо версионируемая библиотека может хранить colocated `SPEC.md`, которая регистрируется в общем индексе.
- R2.5. verification=manual; При смешанном размещении индекс остаётся единой точкой обнаружения, а для одного компонента существует только одна каноническая спека.
- R2.6. verification=manual; Проект с деревом `specs/` содержит `specs/index.md` и `specs/GLOSSARY.md`.
- R2.7. verification=manual; Каждая спека включена в индекс, а индекс не содержит отсутствующих или устаревших путей.
- R2.8. verification=manual; `specs/index.md` оформляется Markdown-таблицей со столбцами `Path`, `Reference`, `Status`, `Summary` именно в этом порядке; для каждого документа предусмотрена ровно одна строка данных.
- R2.9. verification=manual; `Reference` уникален и состоит из строчных ASCII-букв и цифр, разделённых одиночными дефисами.
- R2.10. verification=manual; Статус спеки равен `draft` или `stable` и совпадает со статусом в индексе.
- R2.11. verification=manual; Статус `stable` обозначает обязательный действующий контракт, а расхождение кода с ним является находкой.
- R2.12. verification=manual; Устаревшие требования удаляются или переписываются в текущей спеке; архивные копии, зачёркнутые правила, статус `deprecated` и changelog внутри спеки не используются.
- R2.13. verification=manual; Создание, изменение, перемещение или удаление спеки сопровождается синхронным обновлением индекса и глоссария, если затронуты их данные.

- R3. Структура и содержание спеки:
- R3.1. verification=manual; Каждая спека содержит заголовок с названием компонента, `Status: draft` или `Status: stable` и строку `Spec source of truth for: <компонент/фича>`.
- R3.2. verification=manual; Допустимые заголовки секций: `Overview`, `Scope`, `Definitions`, `Interface`, `Configuration`, `Requirements`, `Implementation`, `Examples`, `Tests`, `Usage constraints`, `Justification`, `Error handling`, `Dependencies`, `Used by`, `Verification`.
- R3.3. verification=manual; Малая спека может опускать необязательные секции; `Tests` обязательна, если хотя бы один листовой R-ID имеет `verification=automated` или `verification=scenario`; при отсутствии таких требований секция может отсутствовать; используемые названия секций остаются стабильными в пределах проекта.
- R3.4. verification=manual; `Scope` определяет области `In` и `Out (non-goals)`.
- R3.5. verification=manual; `Interface` определяет внешние сигнатуры, элементы интерфейса, имена, типы, допустимые входы и выходы и полный перечень кодов ошибок.
- R3.6. verification=manual; `Configuration` присутствует, если существуют параметры, именованные константы или магические числа.
- R3.7. verification=manual; `Requirements` содержит обязательные требования к поведению и свойствам компонента, наблюдаемым его потребителем через публичный интерфейс; внутренние решения, не влияющие на наблюдаемое поведение, в `Requirements` не включаются.
- R3.8. verification=manual; При исправлении ошибки агент добавляет в `Implementation` запись `I-ID`, если она фиксирует внутреннее решение, ограничение или инвариант, необходимые для предотвращения повторения той же ошибки; запись не вводит самостоятельных обязательных правил и не заменяет исправление первопричины или соответствующий `R-ID`, если ошибка затрагивала публичное поведение.
- R3.9. verification=manual; `Examples` поясняет существующие требования и ссылается на соответствующие R-ID, не создавая новых правил.
- R3.10. verification=manual; `Tests` содержит только конкретные автоматизированные проверки и детерминированные многошаговые сценарии, ссылается только на листовые R-ID с `verification=automated` или `verification=scenario` и не ссылается на I-ID; повторение формулировки требования без самостоятельной процедуры не образует методику тестирования.
- R3.11. verification=manual; `Usage constraints` поясняет бюджеты, границы применимости, совместимость, безопасность и предположения об окружении; обязательные ограничения также фиксируются в `Requirements`.
- R3.12. verification=manual; `Justification` содержит стабильные J-ID и ссылки на действующие требования или записи `Configuration`.
- R3.13. verification=manual; `Error handling` поясняет семантику ошибок, определённую в `Requirements` и перечисленную в `Interface`, и не вводит новых кодов или правил.
- R3.14. verification=manual; `Verification` фиксирует проверенные свойства алгоритма, уровень абстракции, фактические результаты и список `Not checked`.
- R3.15. verification=manual; Ни одна секция, кроме `Requirements`, не служит самостоятельным источником обязательств.
- R3.16. verification=manual; Контракт алгоритма описывается шагами, инвариантами и оценками сложности на контрактном уровне, без приватных имён файлов, классов или вспомогательных функций исходного кода.
- R3.17. verification=automated; Каждое семейство prefixed-записей размещается только в соответствующей секции: `R` — `Requirements`, `I` — `Implementation`, `E` — `Examples`, `T` — `Tests`, `J` — `Justification`, `V` — `Verification`; размещение записи этого семейства в любой другой секции запрещено.
- R3.18. verification=automated; Префиксы `R`, `E`, `I`, `V`, `T` и `J` используются для формирования ID записей; каждая непустая строка содержимого в секциях `Requirements`, `Examples`, `Implementation`, `Verification`, `Tests` и `Justification` обязана начинаться с маркера списка `- `, за которым следует ID соответствующего префикса; это правило распространяется на групповые и листовые записи.
- R3.19. verification=automated; Каждая листовая запись `Requirements` содержит ровно один маркер `verification=<значение>` сразу после R-ID; допустимы `automated`, `scenario`, `manual` и `analysis`. `automated` означает, что требование проверяется автоматическим тестом; `scenario` — что существует детерминированный сценарий проверки более чем из одного шага; `manual` — что проверка выполняется человеком по критериям требования; `analysis` — что свойство проверяется аналитическим рассуждением или доказательством.

- R4. Требования и идентификаторы:
- R4.1. verification=manual; Каждое требование имеет стабильный уникальный R-ID; существующие ID не перенумеровываются без явно одобренной миграции с одновременным обновлением ссылок. Пропуски в последовательности ID допустимы; отсутствующий номер не восстанавливается и не заполняется новым требованием без подтверждённого содержания и одобрения.
- R4.2. verification=manual; Требования группируются по смысловым областям с помощью многоуровневых R-ID.
- R4.3. verification=manual; R-ID с дочерними элементами является группой, заканчивается двоеточием и не утверждает поведение.
- R4.4. verification=manual; Листовой R-ID формулирует тестируемое требование и заканчивается точкой.
- R4.5. verification=automated; Каждая prefixed-запись семейств `R`, `E`, `I`, `V`, `T`, `J` занимает ровно одну строку, начинается с маркера списка `- ` в нулевой колонке, после которого сразу следует ID, и не использует Markdown-вложенность для выражения иерархии.
- R4.6. verification=analysis; Каждая листовая запись требования декларативна, однозначна и тестируема.
- R4.7. verification=analysis; Одна строка требования описывает одну поведенческую возможность и не содержит независимых обязательств, обоснований, примеров или пояснений.
- R4.8. verification=manual; Требования ссылаются на имена из `Interface` или `Configuration`, а не на сырые значения параметров, констант, аргументов или магических чисел.
- R4.9. verification=analysis; Локальный термин имеет точное определение в `Definitions` либо `GLOSSARY.md`; нормативные формулировки используют общеупотребительные или определённые термины.
- R4.10. verification=manual; Каждый нетривиальный пример зеркалирует ID объясняемого требования и не создаёт новых обязательств.
- R4.11. verification=manual; Каждая запись `Verification` относится к точно названному алгоритму и не заявляет доказательство полной корректности на основании ограниченного прогона TLC.
- R4.12. verification=analysis; Каждый листовой R-ID описывает свойство или поведение, наблюдаемое потребителем компонента через публичный интерфейс; требование, не влияющее на такое наблюдаемое поведение, удаляется из `Requirements` либо переносится в подходящую ненормативную секцию.
- R4.13. verification=automated; Листовой R-ID с `verification=automated` или `verification=scenario` покрывается как минимум одной записью T-ID, которая описывает соответствующую проверку; для `verification=manual` и `verification=analysis` отдельная запись T-ID не требуется.
- R4.14. verification=automated; Каждая листовая запись T-ID указывает один или несколько проверяемых R-ID, конкретную процедуру проверки, условия или входные данные и критерий ожидаемого результата; пересказ требования без воспроизводимой процедуры не считается тестом.

- R5. Интерфейс и конфигурация:
- R5.1. verification=manual; Каждое публичное имя, сигнатура, тип, допустимый домен и код ошибки определяются в `Interface`.
- R5.2. verification=manual; Каждое обязательное поведение, связанное с интерфейсным доменом, дополнительно формулируется в `Requirements`.
- R5.3. verification=manual; Каждая запись `Configuration` ключуется именем, указывает тип значения и его эффект.
- R5.4. verification=manual; Для параметра `Configuration` указывает допустимые значения и значение по умолчанию.
- R5.5. verification=manual; Для именованной константы `Configuration` указывает идентификатор, единственное значение, единицы измерения при наличии и метку `fixed`, без `default`.
- R5.6. verification=manual; Для безымянного литерала, являющегося магическим числом, `Configuration` задаёт семантическое имя и метку `magic`, без `default`.
- R5.7. verification=manual; Каждое обязательное поведенческое следствие конфигурации связано с актуальным R-ID.
- R5.8. verification=manual; Требования используют имена параметров и констант вместо их числовых значений.

- R6. Термины и межспековые связи:
- R6.1. verification=manual; Каждый проектный термин использует полный ID `<reference>/<term>`.
- R6.2. verification=manual; Обе части term ID состоят только из строчных ASCII-букв, цифр и дефисов.
- R6.3. verification=manual; Каждый новый термин добавляется в `GLOSSARY.md` тем же изменением, что и спека, если проект использует дерево `specs/`.
- R6.4. verification=manual; Для одного полного term ID существует одно определение.
- R6.5. verification=manual; `GLOSSARY.md` оформляется Markdown-таблицей со столбцами `Term ID`, `Definition`, `Defined in` именно в этом порядке; для каждого термина предусмотрена ровно одна строка данных, строки отсортированы по полному term ID в строгом алфавитном порядке.
- R6.6. verification=manual; Ячейка `Defined in` каждой строки глоссария начинается с Reference-префикса термина и при необходимости может содержать связанные ID требований.
- R6.7. verification=manual; Переиспользуемый термин цитируется с полным ID владельца без изменения префикса и не определяется повторно.
- R6.8. verification=manual; Спека-владелец переиспользуемого термина указана в `Dependencies`.
- R6.9. verification=manual; Ссылка на другую спеку использует её `Reference`, а не путь к файлу.
- R6.10. verification=manual; Каждая связь `Dependencies` имеет семантическое основание и зеркальную запись `Used by`.
- R6.11. verification=manual; Обе стороны связи обновляются согласованно, а при исчезновении основания удаляются с обеих сторон.
- R6.12. verification=manual; Проза спеки написана на языке проекта; первая спека использует язык пользователя, а языки в одном файле не смешиваются.
- R6.13. verification=manual; В неанглоязычной прозе не используются незадокументированные англицизмы, кроме полных term ID, идентификаторов и литералов кода, CLI-глаголов и конфигурационных ключей.

- R7. Проверки и отклонения:
- R7.1. verification=scenario; После каждого изменения спеки агент сначала запускает `speclint.py`, затем выполняет семантический проход по изменённой и связанным спекам.
- R7.2. verification=scenario; Механическая проверка и семантический проход сообщаются раздельно.
- R7.3. verification=analysis; Семантический проход проверяет однозначность и тестируемость требований, атомарность поведения, корректность связей, полноту `Configuration`, язык и термины, а также содержательность `Verification`.
- R7.4. verification=scenario; После изменения требования агент проверяет актуальность связанной `Verification` и обновляет либо удаляет устаревшую запись.
- R7.5. verification=manual; `DEVIATIONS.md` содержит только открытые расхождения между действующей спекой и кодом и не используется как changelog или архив.
- R7.6. verification=manual; Если спека изменена без конформного изменения кода в том же изменении, для каждого подтверждённого расхождения создаётся запись в `DEVIATIONS.md`.
- R7.7. verification=manual; Если спека и конформный код изменены вместе, запись о несуществующем открытом расхождении не создаётся.
- R7.8. verification=manual; Каждая запись `DEVIATIONS.md` описывает одно расхождение, имеет стабильный D-ID и содержит дату, идентификатор спеки, `Spec edit`, `Was`, `Now`, `Code impact`, `Tests` и `Review focus`.
- R7.9. verification=manual; `Was` описывает наблюдаемое поведение кода, а `Now` — обязательное поведение обновлённой спеки.
- R7.10. verification=manual; Новые записи отклонений добавляются в конец файла; ID не перенумеровываются.

## Implementation

- I1. Скилл реализован инструкцией `SKILL.md` и скриптом `speclint.py`. Инструкция описывает процесс spec-first, правила формата спек, индекса и глоссария, проверку изменений, учёт открытых расхождений и реализацию по утверждённому контракту.
