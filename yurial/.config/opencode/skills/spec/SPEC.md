# Скилл `spec`: спецификация

Status: draft
Spec source of truth for: скилл opencode `spec` — авторинг проектных спецификаций, spec-first flow, механические проверки спек

Документ фиксирует функциональность скилла `spec`: назначение, условия применения, состав, контракты на спек-документы, интерфейс скрипта `speclint`, ограничения. Источник фактов — `SKILL.md` скилла и скрипт `speclint` из каталога скилла. Каталог скилла в репозитории: `yurial/.config/opencode/skills/spec/`.

## Назначение

Скилл регламентирует авторинг, размещение и изменение проектных спецификаций — документов, фиксирующих поведение алгоритмов, функций, компонентов и систем: их интерфейсы, семантику, ограничения, обработку ошибок.

Базовый принцип: спека — источник истины. Код следует спеке и не противоречит ей. Поведение, найденное в коде, но отсутствующее в спеке, — либо пробел спеки (правится спека), либо баг (правится код); молчаливо терпеть его нельзя.

Охватываемые области (нумерация разделов SKILL.md):

- безоговорочные правила и spec-first flow (раздел `1`);
- порядок авторинга спеки через делегирование субагентам (раздел `1b`);
- раскладка спек по размеру проекта (раздел `2`);
- форматы `specs/index.md` и `specs/GLOSSARY.md` (разделы `3`, `3a`);
- шаблон спек-файла и правила написания (раздел `4`);
- пост-измененческие проверки: механический проход `speclint` и семантический проход из восьми проверок (раздел `5`);
- учёт открытых расхождений код↔спека в `DEVIATIONS.md` (раздел `6`);
- дисциплина соответствия кода спеке при реализации и ревью (раздел `7`);
- каталог анти-паттернов (раздел `8`).

## Триггеры применения

Из description в frontmatter SKILL.md скилл применяется:

- при написании, обновлении или ревью спек-документов: `SPEC.md`, `specs/<component>.md`, `specs/index.md`, `specs/GLOSSARY.md`, colocated `<library>/<component>/SPEC.md`;
- при любом запросе на изменение функциональности, поведения или ограничений — spec-first flow: спека до кода;
- при проверке связанных спек на коллизии;
- при реализации кода по существующей спеке.

Запрещённые случаи: README и общая документация проекта (для них — скилл `docs`), TLA+-спеки, TLC-модели и доказательства (скиллы `tla-plus`, `tlc-run`, `tlaps`). Скилл применяется только к спек-документам и spec-driven изменениям.

## Компоненты скилла

### SKILL.md

Инструкция скилла (загружается при активации): назначение, безоговорочные правила, порядок авторинга, раскладка, форматы индекса и глоссария, шаблон спек-файла с правилами написания, протокол пост-измененческих проверок, регламент `DEVIATIONS.md`, правила соответствия код↔спека, анти-паттерны. Frontmatter: `name: spec` и `description` (триггеры применения, включая исключение TLA+/TLC/доказательств).

### speclint

Скрипт механических проверок спек-файлов (`#!/bin/sh` + awk), поставляется в каталоге скилла. Проверяет формат prefixed-записей (R, A, V, T, J), однострочность и плоскость их списков, голые числовые литералы, индекс и глоссарий (подробно — «Интерфейс speclint»). Скрипт сопровождается тест-набором — каталог `tests/` в каталоге скилла (sh, без внешних зависимостей), покрывающим проверки глоссария и базовые проверки спек-файла и индекса. SKILL.md (раздел `5`) требует запускать его механическим проходом после каждого изменения спеки — до семантического прохода.

## Контракты

Правила, которые скилл накладывает на спек-документы и процесс их изменения.

### Безоговорочные правила (раздел `1`)

- Spec-first: запрос на изменение функциональности — это запрос на изменение спеки. Порядок: найти управляющую спеку → обновить её → проверить связанные спеки на коллизии → только затем реализовывать. Коммит, меняющий поведение, затрагивает спеку в том же изменении (или ссылается на раздел спеки, уже предписывающий это поведение).
- Никаких противоречий: код не расходится со спекой. Если ограничения реализации вынуждают отклонение — стоп и эскалация конфликта пользователю; изменение спеки — решение, а не побочный эффект кодинга.
- Одна каноническая спека на компонент: двух спек одного и того же не держать; из вспомогательных документов — ссылка на каноническую.
- Индекс актуален всегда: в проекте с индексом (раздел `2`) каждое создание/обновление/перемещение/удаление спек-файла обновляет `specs/index.md` тем же коммитом.
- Конфликт спеки со спекой останавливает работу: если разрешение неочевидно, обе формулировки передаются пользователю, пауза; победителя молча не выбирать.

### Порядок авторинга (раздел `1b`)

- Исследование — агент `assistant_low`: читает релевантные спеки, исходники, документацию; сохраняет черновик (например `specs/draft.md` или рабочая копия в корне проекта) со ссылками на файлы/URL с точными диапазонами строк, краткими резюме релевантности каждого документа, отмеченными конфликтами и неоднозначностями между документами, пробелами документации. Черновик создаётся локально для просмотра автором и не входит в финальный коммит.
- Генерация — агент `assistant_heavy`: пишет или обновляет спеку по шаблонам и правилам (разделы `3`–`4` SKILL.md); черновик — источник ссылок и пробелов; спека цитирует конкретные ID требований, поддерживает двунаправленные связи (Dependencies/Used by), следует правилам раскладки и формата.
- Зачистка: после генерации и прохождения проверок (раздел `5`) черновик удалить либо перенести из корня репозитория в архив (например `specs/drafts/` с временной меткой или под `.gitignore`). Коммитить черновик можно только при явном одобрении и только если он содержит значимую методологию или обоснование, ценное для будущего использования.

### Раскладка по размеру проекта (раздел `2`)

| Проект | Размещение спек | Индекс |
|---|---|---|
| Малый (один компонент) | `SPEC.md` в корне репозитория | нет |
| Крупнее (несколько компонентов/фич) | `specs/<component-or-feature>.md` | `specs/index.md` |
| Монорепозиторий нескольких библиотек | colocated `<library>/<component>/SPEC.md` — разрешено, но обязательно индексируется в `specs/index.md` | `specs/index.md` |

Правила:

- рост сверх «малого»: при появлении второй компонентной границы или превышении корневым `SPEC.md` ~`300` строк — разбиение на `specs/` с индексом; содержимое корневой спеки переносится в `specs/<component>.md`, дублирование запрещено (допустима однострочная заглушка-указатель по старому пути, если на него широко ссылаются);
- порог colocation: несколько независимо версионируемых библиотек в репозитории (их компоненты живут далеко от централизованного дерева `specs/`); репозиторий одной библиотеки держит всё в `specs/`;
- смешанная раскладка (часть colocated, часть централизованно): индекс — единственная точка обнаружения, обязан перечислять все спеки независимо от места файла;
- не индексировать несуществующий путь; не оставлять существующую спеку без строки в индексе (colocated — классическая утечка, аудировать явно);
- мультикомпонентный проект несёт два сквозных файла: `specs/index.md` и `specs/GLOSSARY.md`; оба сопровождаются теми же коммитами, что и описываемые ими спеки.

### Формат specs/index.md (раздел `3`)

Таблица с колонками `Path`, `Reference`, `Status`, `Summary`.

- `Status`: `draft` — проектируется, может меняться свободно, код может следовать предварительно, но отклонения ещё не баг; `stable` — реализована, обязательна, расхождение кода со спекой — находка. Статуса `deprecated` нет: заменённые спеки (или их устаревшие части) удаляются или переписываются на месте под новые требования; строка индекса удаляется тем же коммитом; заглушка по старому пути при наличии спеки-преемника не оставляется. История живёт в git, не в актуальных спек-файлах.
- `Summary`: одна строка, существительные — что фиксирует, а не как.
- `Reference` — стабильный ID, которым цитируют спеку вместо путей (раздел `4`); содержит имя компонента или библиотеки, может быть составным (`library-component`, например `yt-core-bus`; составная форма — когда короткое имя компонента неоднозначно между библиотеками); уникален, стабилен, строго английский — по аналогии с term ID: строчные ASCII-буквы и цифры, разделённые одиночными дефисами; не-ASCII буква (кириллица и любой иной алфавит) или заглавная буква — нарушение; иную пунктуацию (underscore, точку) белый список линта не пропускает. Переименование обновляет одним коммитом индекс, Dependencies всех ссылающихся спек и все term ID с этим префиксом (GLOSSARY.md и тексты спек).
- Дополнительные колонки (owner, last-updated) допустимы, если команда их ведёт; протухшая дополнительная колонка хуже отсутствующей.

### Формат specs/GLOSSARY.md (раздел `3a`)

Таблица с колонками `Term`, `Definition`, `Defined in`.

- каждый терм — полный ID `<reference>/<term>` (например `yt-core-bus/connection`), строго английский, при каждом употреблении: глоссарий, секции Definitions, тексты требований. Префикс обязан равняться существующему reference из `specs/index.md`; короткая форма (`connection`) не используется. «Строго английский» относится к term ID и определён механически: обе части ID (префикс-reference и терм) состоят из строчных ASCII-букв, цифр и дефисов; не-ASCII буква (кириллица и любой иной алфавит) либо заглавная буква в любой из частей — нарушение при каждом употреблении; смешение алфавитов внутри одного term ID (например `очередь/lease` или `queue/очередь`) запрещено. Текст Definition и проза глоссария следуют языку спек проекта (правило языка — раздел `4`).
- сортировка по полному term ID строго алфавитная, всегда: глоссарий — справочник, а не текст для чтения.
- одна строка на term ID; `Defined in` цитирует владеющий reference — обязанный равняться префиксу термина, опционально с ID требований; никогда — путь файла.
- глоссарий — каноническое место видимости «какая спека каким термином владеет»: терм, введённый спекой (её секцией Definitions), получает строку тем же коммитом; терм, переиспользуемый из другой спеки, повторно не определяется — его строка продолжает указывать на спеку-владельца.
- одно значение на term ID в проекте; префикс разводит коллизии: `queue/lease` и `auth/lease` — разные термины, могут сосуществовать; если два reference определяют одно короткое имя одного концепта — переиспользовать полный ID владельца вместо дублирования (проверка общего словаря, раздел `5`).
- глоссарий обновляется вместе с индексом: создание/удаление/переименование спеки — оба файла одним коммитом; строка, цитирующая удалённый reference, или префикс, который больше не разрешается, — висячая ссылка; чинить или удалять немедленно.
- малые проекты с одним `SPEC.md`: достаточно секции Definitions внутри `SPEC.md` в той же форме полных ID (reference — имя компонента, объявленное в заголовке спеки); `GLOSSARY.md` вводится с появлением дерева `specs/`.

### Шаблон спек-файла (раздел `4`)

Заголовок: название компонента, `Status: stable | draft`, строка `Spec source of truth for: <компонент/фича>`. Секции:

- `Overview` — что компонент делает и зачем существует; место системных объяснений; может цитировать ID требований. Строки требований объяснений не несут — пояснения к требованиям живут в Examples (записи Ax.y), обоснования решений — в Justification (записи Jx.y).
- `Scope` — `In:` явный список ответственностей; `Out (non-goals):` чего компонент заведомо не делает.
- `Definitions` — термины с точным значением, каждый — полный ID `<reference>/<term>`; только английский.
- `Interface` — сигнатуры, эндпоинты, CLI-глаголы, схемы сообщений, конфиг-ключи — внешне наблюдаемый контракт; каждый элемент именован и типизирован. Здесь живёт контракт аргументов: допустимые значения каждого аргумента (вход) и каждого результата (выход), включая коды ошибок — полный перечень кодов ошибок объявляется в Interface как допустимые значения результата. Имена и типы конфиг-ключей — здесь; допустимые значения и эффект — в Configuration. Error handling несёт семантику кодов, но не их перечисление.
- `Configuration` — обязательна при наличии настраиваемых параметров, именованных констант или магических чисел; отсутствие секции утверждает, что ни одного из трёх нет (сворачивание секций в малых спеках этого не отменяет). Одна строка на элемент, три всегда различимых вида, каждая строка ключуется именем, никогда значением: параметр — ключ конфиг-ключа; тип/границы/enum/шаг, default, эффект; именованная константа — значение, зашитое в код под идентификатором (`MAX_RETRIES`), ключ — идентификатор, единственное значение с единицами, пометка `fixed`, default нет; магическое число — голый литерал без идентификатора (`3`, `60000`), ключ — семантическое имя, выбранное спекой, нижним регистром через дефис как reference ID (например `batch-timeout-cap`); имя живёт только в спеке, никогда в коде, строка отмечает, что код несёт безымянный литерал (это отличает `magic` от `fixed`), единственное значение с единицами, пометка `magic`, default нет. Поведение остаётся в Requirements — строка Configuration цитирует их ID.
- `Requirements` — правила последовательности, гарантии порядка, семантика алгоритмов (шаги или инварианты, не код) — нумерованными требованиями со стабильными ID: плоскими (R1) или многоуровневыми (R2.1, R4.2.1), любой глубины. Каждый лист — тестируемое требование; ID с детьми — группа: строка-заголовок, оканчивающаяся двоеточием, поведения не утверждает, называет то, чем управляют её дети. Каждая запись занимает ровно одну строку файла. Записи образуют плоский список: каждая строка записи начинается от левого поля, ребёнок (R2.1) никогда не вложен отступом под родителя (R2) — иерархию выражает только многоуровневый ID, не markdown-вложенность. Предложения декларативные; строка может нести несколько предложений, каждое — без соединения независимых клауз и не более чем с одним придаточным условия или времени. Строка требования декларирует правило — без объяснений и обоснований (они — в Overview, Examples и Justification). Требование цитирует имена, не значения: параметр, константу, аргумент — по идентификатору из Interface или Configuration; магическое число — по его семантическому имени, выбранному спекой в Configuration (см. выше). Одна поведенческая фича на строку. Словарь — общеупотребительный с общепринятыми терминами; локальные термины — только с зафиксированной в Definitions интерпретацией и строкой в GLOSSARY.md; формулировки однозначны для читателя. Цитаты — ID и диапазоны ID; цитата покрывает ID вместе со всем поддеревом; диапазон — все ID от первого до последнего endpoint, поддеревья включительно.
- `Examples` — опциональна; присутствует, когда любому требованию нужна иллюстрация или пояснение. Одна запись на объясняемое требование, A-ID зеркалит R-ID (A2.1 объясняет R2.1; A2 — группу R2 с поддеревом); конкретные примеры вход→выход и пояснения; новых требований не вводит; одна запись занимает ровно одну строку.
- `Tests` — опциональна; присутствует, когда требования покрыты записанными тестами. Одна запись на тест: стабильный ID, плоский (T1) или многоуровневый (T1.1), те же правила синтаксиса ID, что и у R-ID (уникальность, без перенумерации, многоуровневость); ID с детьми — группа-заголовок с двоеточием; лист цитирует ID покрываемых требований, каждый процитированный R-ID называет существующее требование; одна запись занимает ровно одну строку, любой длины.
- `Usage constraints` — ограничения применения компонента, навязанные извне: бюджеты (ёмкость, латентность), границы применимости, совместимость (версии, форматы), безопасность, предположения об окружении. Внутренние лимиты и поведение здесь не живут: поведение — в Requirements, самоисполняемые зашитые пределы — в Configuration.
- `Justification` — опциональна; присутствует, когда существует и значимо обоснование выбранных default-значений, деталей алгоритмов или формул; иначе отсутствует. Одна запись на обоснованное решение: стабильный ID, плоский (J1) или многоуровневый (J2.1), те же правила синтаксиса ID, что и у R-ID; проза, цитирующая ID обосновываемых требований или Configuration-строк; одна запись занимает ровно одну строку.
- `Error handling` — семантика кодов ошибок, перечисленных в Interface: классы, семантика повторов, поведение при частичных сбоях; перечисление кодов не повторяет.
- `Dependencies` — спеки, чьи термины, интерфейсы или ограничения данная спека использует или ограничивает (семантические связи); цитирование по reference ID из индекса, опционально с ID требований.
- `Used by` — обратная сторона Dependencies, ведётся в цитируемых спеках: каждая спека из Dependencies обязана иметь обратную запись в своём Used by (с тем же смыслом со своей стороны); заполняется изменением ссылающейся спеки тем же коммитом.
- `Verification` — одна запись на проверенный алгоритм (спека может описывать несколько — всегда точное имя, никогда просто «алгоритм»); заполняется при проверке алгоритма средствами TLC/TLAPS (правила запуска — скиллы tla-plus/tlaps) и цитирует ID требований алгоритма; стабильный ID, плоский (V1) или многоуровневый (V2.1), те же правила синтаксиса ID; одна запись занимает ровно одну строку, поля разделены точкой с запятой: уровень абстракции проверки (L0/L1/L2 tla-plus или кастомное описание) и то, что этот уровень абстрагирует — уровень верификации, а не спеки; `Checked` — ровно то, что установил прогон: TLC — ограниченные свидетельства (границы модели фиксируются), TLAPS — доказательство (фиксируется модуль доказательства); слово «verified» для выборочного TLC запрещено; `Not checked` обязателен — намеренные пробелы (непроверенные границы, немоделируемые классы сбоев, пропущенная liveness, отсутствие доказательства); запись без списка Not checked завышает результат. Изменение поведения проверенного алгоритма инвалидирует запись: перезапустить и обновить либо удалить (с отметкой в записи DEVIATIONS.md об этом изменении); протухшая запись, утверждающая верификацию несуществующего поведения, хуже отсутствующей.

Малые спеки могут сворачивать секции; заголовок (Status, скоуп, ID) и имена секций стабильны по проекту.

### Правила написания (раздел `4`)

- Ссылки между спеками — reference ID, никогда пути файлов: единственный валидный способ цитировать другую спеку — её `Reference` из `specs/index.md` (пути ломаются при перемещении файлов между корневым SPEC.md, specs/ и colocated-раскладками); правило действует везде — Dependencies, Definitions, тела требований.
- Термины — полные ID, строго английские, при каждом употреблении (Definitions, тела требований, Usage constraints, GLOSSARY.md): «строго английский» определён механически — обе части ID (префикс-reference и терм) состоят из строчных ASCII-букв, цифр и дефисов; не-ASCII буква (кириллица и любой иной алфавит) либо заглавная буква в любой из частей и смешение алфавитов внутри одного term ID (например `очередь/lease` или `queue/очередь`) — нарушение при каждом употреблении. Префикс разрешается в существующий reference — из индекса или имя компонента из заголовка спеки в малых проектах без индекса. Переиспользование чужого термина разрешено и предпочтительнее переопределения: полный ID владельца дословно (префикс не отрезать и не перешивать), спека-источник — в Dependencies.
- Связи семантические, двунаправленные, точные: запись Dependencies существует, только пока спека фактически использует термины, интерфейсы или ограничения другой спеки в нормативном содержимом (требования, определения, интерфейс) — не для исторических или «смежных» упоминаний; оба конца пишутся одним коммитом; исчезновение семантической основы (требование удалено или переписано, термин заменён) — удаление связи с обеих сторон одним коммитом; односторонние и «на всякий случай» связи не оставляются.
- Формулировки декларативные и тестируемые, одна поведенческая фича на строку: составные требования, объединяющие несколько фич, запрещены — дробить на отдельные; prefixed-запись — требование (R), запись Examples (A), запись Verification (V), запись Tests (T), запись Justification (J) — занимает ровно одну строку файла, перенос на несколько строк запрещён при любой длине строки. Prefixed-записи образуют плоский список: каждая строка записи начинается от левого поля, отступ перед записью запрещён, ребёнок (R2.1) не вкладывается под родителя (R2) — иерархию выражает только многоуровневый ID, не markdown-вложенность. Обоснования, мотивация, примеры внутри строки требования запрещены; системное обоснование — в Overview, обоснование решения — в Justification (записи Jx.y), примеры и пояснения к требованиям — в Examples (записи Ax.y). Требование, которое нельзя опровергнуть тестом, — заметка, а не требование.
- Стабильные ID не перенумеровываются никогда: устаревшее требование изымается (retire — удалить формулировку, факт изъятия отметить в DEVIATIONS.md); на ID ссылаются комментарии кода, тесты, коммиты. Тот же порядок управляет остальными семействами prefixed-записей — Examples (Ax.y), Verification (Vx.y), Tests (Tx.y), Justification (Jx.y): ID уникальны в пределах семейства, не перенумеровываются, многоуровневые разрешены (Rx.y.z, любая глубина; каждый ID на каждом уровне уникален, правила запрета перенумерации и изъятия действуют на каждом уровне одинаково). Семейства разделяет только синтаксис ID: правило концевой пунктуации R (лист оканчивается точкой, группа — двоеточием) применяется только к записям R. ID с детьми — группа, не требование: строка-заголовок с двоеточием, поведения не утверждает. Цитата ID покрывает его вместе со всем поддеревом; диапазон — все ID между endpoint, поддеревья включительно.
- Конкретные примеры вход→выход для каждого нетривиального правила — в Examples как записи Ax.y, зеркалирующие ID объясняемых требований; строка требования примеров и пояснений не несёт.
- Алгоритмы записываются как поведение (шаги, инварианты, оценки сложности), не как реализация — без файлов исходников, имён классов, приватных хелперов.
- Контракт аргументов входа/выхода — в Interface: для каждого метода, эндпоинта, CLI-глагола, схемы сообщения Interface объявляет допустимые значения каждого аргумента и результата; коды ошибок — допустимые значения результата, полный их перечень объявляется в Interface; Error handling — только семантика (классы, повторы, частичные сбои). Исключение — настраиваемые параметры: их допустимые значения и эффект — в Configuration, Interface несёт лишь имена и типы конфиг-ключей.
- Configuration обязательна при наличии настраиваемых параметров, именованных констант или магических чисел: любой конфиг-ключ, флаг, переменная окружения, ручка тюнинга либо зашитое в поведение фиксированное значение (таймаут, лимит, порог, размер буфера, счётчик повторов и т.п.) получает строку с допустимыми значениями (для параметра: тип, границы или enum, шаг, default, единицы; для фиксированного значения обоих видов: единственное значение с единицами и пометкой `fixed`/`magic`, без default) и эффектом (для параметра: что различается при разных значениях, граничные случаи, взаимодействия; для фиксированного: к чему приводит значение); каждая строка ключуется именем, никогда значением; само поведение остаётся в Requirements — строка цитирует их ID. Лимит, навязанный самим компонентом через зашитое значение, — фиксированное значение в Configuration, а не запись в Usage constraints: Usage constraints держит внешние бюджеты и границы применимости, не самоисполняемые пределы.
- Требования цитируют имена, не значения: имя — стабильный handle (значения перетюниваются, различаются по развёртываниям, приходят в вызовах); требование, описывающее поведение, управляемое параметром, константой, магическим числом или аргументом, ссылается на имя — конфиг-ключ, идентификатор константы, имя аргумента или семантическое имя магического числа, выбранное спекой, точно как спека ключует его в Interface или Configuration. Литерал в строке требования — находка всегда: магическое число сначала записывается в Configuration под выбранным спекой семантическим именем (например `batch-timeout-cap`), требование цитирует имя, никогда литерал; default или граница — факт о параметре, несомый его Configuration-строкой, не требованием. Механический линт (раздел `5`) исполняет запрет универсально: голый числовой литерал в любой секции, кроме Configuration и Examples, — ошибка. Дословный пример из SKILL.md: «R1.2 При достижении exitTimeout процесс завершается.» — цитируется имя параметра `exitTimeout`, а не значение `30s`.
- Язык: следовать существующему языку спек проекта; первая спека проекта — на языке пользователя; языки в одном файле не смешивать. Без англицизмов: проза неанглоязычной спеки — словами этого языка, английские заимствования запрещены; концепт без родного слова вводится определённым термином (полный ID), а не адхок-заимствованием. Дословные исключения: term ID всегда английские; идентификаторы и литералы кода (`MAX_RETRIES`, `put(k, v)`, CLI-глаголы, конфиг-ключи) — артефакты кода, не проза.
- Спека фиксирует только текущие требования: устаревшие формулировки переписываются или удаляются; зачёркнутые архивы и change log внутри спек-файлов запрещены; DEVIATIONS.md записывает только результирующее расхождение кода со спекой, а не само изменение.
- Записи Verification: спека с алгоритмами получает секцию Verification при проверке любого из них формальным инструментом — правила полей и жизненного цикла см. в шаблоне выше.
- Записи Tests: при покрытии требований записанными тестами спека несёт секцию Tests — одна запись на тест, стабильный T-ID, лист цитирует покрываемые R-ID, каждый из которых называет существующее требование; тест на каждый ID требования — ожидание по умолчанию (раздел `7`).
- Трёхместная синхронизация форматных правил: правило формата живёт в трёх согласованных местах — шаблон (раздел `4`), список правил написания, анти-паттерны (раздел `8`); изменение правила обновляет все три места одним коммитом.

### Пост-измененческие проверки (раздел `5`)

Выполняются всегда, до реализации.

Механический проход: `speclint` по изменённым спек-файлам, а при затрагивании — по `specs/index.md` и `specs/GLOSSARY.md`. Все находки чинятся до семантического прохода. Состав проверок — «Интерфейс speclint» ниже.

Семантический проход по связанным спекам (обнаруживаются через индекс, Dependencies и общий словарь):

- Общие идентификаторы: имена, term ID, поля сообщений, конфиг-ключи, коды ошибок, единицы (ms vs s), версии — одно имя везде означает одно и то же.
- Прямые противоречия: одна спека требует того, что другая запрещает (порядок, дефолты, семантика ошибок, лимиты).
- Дрейф контрагентов: продюсерская спека добавила поле/состояние/флаг, о котором потребительская спека не упоминает; спека начала зависеть от ограничения, которое другая спека убрала.
- Дубли определений: одно правило теперь заявлено в двух спеках — канонической остаётся одна формулировка, из другой — ссылка.
- Разрешение ссылок: каждый reference ID из Dependencies/Definitions и каждый префикс термина изменённой спеки существует в `specs/index.md`; переименование или удаление reference не оставляет висячих цитат и осиротевших префиксов (пути в цитатах — сами находка). Для GLOSSARY.md: строки цитируют существующие reference (равные префиксу термина), алфавитный порядок, покрытие всех терминов, которые изменённая спека ввела или перестала использовать; язык term ID в строках глоссария проверяется механически («Интерфейс speclint»). Язык term ID в текстах спек (Definitions, тела требований) — семантический проход и ревью.
- Симметрия и семантическая валидность связей: каждой записи Dependencies изменённой спеки — парная запись Used by в цитируемой спеке (и наоборот для спек, чей Used by ссылается на изменённый reference); каждая выжившая связь прослеживается до конкретного требования, определения или элемента интерфейса, который её использует; связь с уничтоженной или переписанной основой удаляется из обеих спек.
- Устаревание верификации: изменение требований, цитируемых Verification-записью (поведение алгоритма), инвалидирует её — перезапуск и обновление либо удаление; влияние на верификацию отмечается в записи DEVIATIONS.md об этом изменении.
- Покрытие Configuration: каждый параметр, который изменение делает настраиваемым (или перетюнивает), и каждое фиксированное значение, которое оно вводит или меняет (именованная константа, магическое число), имеет Configuration-строку с допустимыми значениями (единственное значение `fixed`/`magic` для фиксированного) и эффектом; строки, цитирующие изменившиеся или изъятые ID требований, обновляются тем же коммитом.

Резолюция: механические фиксы (переименования, обновление ссылок, упоминания у контрагента) чинятся; если обе формулировки выглядят намеренными — стоп и вопрос пользователю: это дизайн-конфликт, а не опечатка.

### DEVIATIONS.md (раздел `6`)

- Изменения целевого поведения вносятся в спеку немедленно, тем же коммитом, что и изменение. Правящее изменение спеки открывает расхождение между обновлённой спекой (новым источником истины) и кодом, который теперь должен догнать спеку, — и только это расхождение записывается в `DEVIATIONS.md`: корень — малые проекты, `specs/DEVIATIONS.md` — проекты с деревом specs/. Назначение файла: ответить, какой код доработать и что проверять ревьюеру этого кода. Правящее изменение спеки без записи в DEVIATIONS.md неполно — если конформный код не ложится тем же коммитом.
- Запись — открытое расхождение, а не история: запись существует, только пока описываемое ею расхождение код↔спека открыто; сам факт существования записи утверждает «этот код ещё не соответствует спеке». `Was`/`Now` описывают текущее состояние расхождения: слева — что код всё ещё делает, справа — что предписывает обновлённая спека. Нет открытого расхождения — нет записи. Файл — не changelog и не история изменений спек (история — в git). Конформный код в том же коммите, что и правка спеки, записи не порождает.
- Формат записи (добавление в конец, новые ниже): заголовок `D-<номер> <дата> <спека>`; `Spec edit` — что изменено, с цитатами ID требований; `Was` — что код всё ещё делает; `Now` — что предписывает обновлённая спека; `Code impact` — места доработки (файлы/модули здесь разрешены — в отличие от самой спеки, потому что ворклист существует для драйва правок кода); `Tests` — инвалидированные и заменяемые тесты; `Review focus` — что ревьюер обязан проверить для соответствия новой спеке (проверки, которых без этого изменения не было бы).
- Правила: одна запись на одно правящее изменение спеки (одно открытое расхождение); стабильные ID (`D-1`, `D-2`, ...), не перенумеровывать. `Was`/`Now` заявляют наблюдаемое поведение, не реализацию. Правки записей задним числом запрещены: коррекция — новой записью со ссылкой на старую, заменённая удаляется тем же коммитом (ссылка разрешается через историю git). Жизненный цикл завершается соответствием: код соответствует новой спеке (реализация есть, тесты обновлены и зелёные) — запись удаляется тем же коммитом, что и конформный код, не позже; обнаруженная уже-соответствующей запись удаляется немедленно. Малые проекты могут завести DEVIATIONS.md в корне ещё до появления дерева specs/.

### Соответствие код↔спека (раздел `7`)

- Реализация по спеке: цитировать ID требований (сообщение коммита или текст PR); тест на каждый ID требования — ожидание по умолчанию; записанные тесты несут стабильные T-ID, цитирующие покрываемые R-ID (раздел `4`, Tests).
- Реализация записи DEVIATIONS.md: цитировать её D-ID; когда код стал конформен новой спеке — удалить запись тем же коммитом.
- Встречено неспецифицированное поведение при кодинге: молча не импровизировать — расширить спеку (очевидный механический пробел) либо спросить.
- Запрещено править спеку задним числом под то, что код уже делает, без флага пользователю: такая переписка — это diff между «задуманным» и «фактическим» и должна быть видна пользователю.
- Ревью кода по спеке: любое поведение без подкрепляющего требования — находка (пробел спеки или баг), репортится, не пропускается.
- Ревью кода, реализующего девиацию: явно пройти список Review focus записи до одобрения.

### Анти-паттерны (раздел `8`)

Каталог находок по областям; каждая находка репортится, не пропускается. Форматные записи зеркалят шаблон и правила раздела `4` — три места меняются вместе.

- Spec-first и change flow: коммит поведения без изменения спеки (дрейф); правящее изменение спеки без записи DEVIATIONS.md (кроме конформного кода тем же коммитом); DEVIATIONS.md как архив или changelog — записи, выжившие после соответствия, либо чтение Was/Now как истории «что было и что стало»; хранение заменённых спек или их частей «для справки»; зачёркнутые архивы и change log внутри спек-файлов; тихое разрешение конфликта спек правкой одной стороны.
- Раскладка и индекс: две спеки одного компонента (корневой SPEC.md + копия в specs/, централизованная + colocated) — одна каноническая, другая указатель; colocated `<library>/<component>/SPEC.md` вне индекса; строки индекса на удалённые или перемещённые файлы; протухший Status; неанглийский Reference в индексе — кириллица или иной не-ASCII алфавит в reference, заглавные буквы — белый список линта его отвергает.
- Связи и цитирования: перенумерация требований; цитирование спеки путём файла вместо reference ID; односторонние связи; формальные связи без семантической основы («смежные спеки» из вежливости); использование термина другой спеки без записи её в Dependencies.
- Термины и глоссарий: голые термины (без префикса-reference); неанглийский term ID — кириллица или иной не-ASCII алфавит в любой из частей (`queue/очередь`), смешение алфавитов внутри одного term ID (`очередь/lease`), заглавная буква в term ID (`auth/Lease`); англицизмы в неанглоязычной прозе спеки; рассинхрон GLOSSARY.md — пропущенные строки введённых терминов, висячие строки удалённых reference, Defined in ≠ префиксу термина, нарушенный алфавитный порядок, два определения одного term ID.
- Формат требований: спека как повествование без тестируемых утверждений и ID; составное требование, объединяющее несколько фич; prefixed-запись (R, A, V, T, J), разорванная на несколько строк файла — одна запись, одна строка, перенос запрещён при любой длине; prefixed-запись, вложенная отступом под родителя (ребёнок R2.1 markdown-вложен под R2) — плоский список, иерархию выражает только многоуровневый ID; соединённые независимые клаузы или стопка придаточных в предложении требования; объяснение, обоснование, мотивация или пример внутри строки требования (обоснование решения — запись Jx.y в Justification, цитирующая живые ID; пример — запись Ax.y в Examples); строка группы, утверждающая поведение, или лист с детьми; запись Examples без парного требования (висячее пояснение); запись Justification (Jx.y) без живого требования или Configuration-строки (висячее обоснование); записанные тесты без стабильного T-ID или запись Tests, не цитирующая живой R-ID (без R-ID вовсе или цитирующая несуществующее требование) — висячий тест ничего спек-подкреплённого не проверяет; неопределённые локальные термины (проектный жаргон без Definitions и GLOSSARY); расплывчатые формулировки («handles it reasonably», «usually fast»).
- Interface и Configuration: домены значений аргументов или результатов вне Interface (или нигде); параметр, именованная константа или магическое число без Configuration-строки либо без допустимых значений или эффекта; смешение видов фиксированных значений — magic записана как fixed (код несёт безымянный литерал, не идентификатор) либо именованная константа понижена до magic; строка `magic` ключуется семантическим именем, выбранным спекой, и отмечает безымянный литерал, который реально несёт код, — имя живёт только в спеке; повышение литерала до именованной константы — изменение кода, и только тогда строка становится `fixed` под идентификатором из кода; цитирование значения вместо имени в строке требования («процесс завершается через `30` s», где правило — «по достижении exitTimeout»; «выше `60000` ms», где правило — «выше `batch-timeout-cap`») — значения перетюнируются и различаются по развёртываниям; стабильная ссылка — имя, объявленное в Interface/Configuration (идентификатор кода или семантическое имя магического числа, выбранное спекой).
- Структура и скоуп: спека, детализирующая приватную реализацию (заманивает рефакторинг в контракт); расхождение единиц и именования со смежными спеками.
- Верификация: заявления «verified»/«tested» об алгоритмах без Verification-записи; записи без точного алгоритма (в мультиалгоритмной спеке), без стабильного V-ID или разорванные на несколько строк (одна запись, одна строка, поля через точку с запятой), без уровня абстракции, без списка Not checked; заявление доказательства за ограниченные TLC-свидетельства; запись, пережившая изменение поведения алгоритма.

## Интерфейс speclint

### Синтаксис и аргументы

```
speclint <path>...
```

Минимум один путь; иначе `usage:` в stderr и код `2`. Путь — `.md`-файл (спека, `index.md`, `GLOSSARY.md`) или директория.

### Режимы

- Директория: рекурсивно и в сортированном порядке линтятся все `index.md` (при этом собираются reference ID), затем все `GLOSSARY.md`, затем все прочие `.md`. Тип файла определяется по базовому имени: любой `index.md`/`GLOSSARY.md` в дереве трактуется как индекс/глоссарий; прочие `.md` — как спеки.
- Файл `index.md` — линт индекса.
- Файл `GLOSSARY.md` — линт глоссария; если reference ID ещё не собраны и в той же директории лежит `index.md`, он линтится автоматически; иначе проверка разрешения префиксов пропускается с предупреждением в stderr (вклад в код выхода — `1` при отсутствии ошибок).
- Прочий `.md` — линт спек-файла.
- Не-`.md` файл либо несуществующий путь — сообщение в stderr, учитывается как ошибка (вклад в код `2`).

### Проверки спек-файла

- строка требования соответствует шаблону `- R<цифры>(.<цифры>)*[.] Текст`; за ID непосредственно обязан следовать `. ` (точка и пробел) — иначе ошибка формата;
- лист оканчивается `.`, группа — `:`; иное окончание строки требования — ошибка;
- ID с детьми обязан быть группой (строка-заголовок), ID без детей — листом; группа без детей — ошибка;
- ID требований уникальны в файле;
- все предки каждого ID существуют и являются группами;
- каждая запись Examples `A<x>` зеркалит существующий ID `R<x>`;
- строки verification соответствуют `- V<цифры>(.<цифры>)*[.] Текст`, ID verification уникальны;
- строки tests соответствуют `- T<цифры>(.<цифры>)*[.] Текст`, ID тестов уникальны, каждая листовая запись Tests цитирует ID требования R, и каждый R-ID, процитированный записью Tests (включая endpoint диапазона ID, например `R3`-`R7`), называет существующее требование; цитирования V и J не проверяются;
- строки justification соответствуют `- J<цифры>(.<цифры>)*[.] Текст`, ID justification уникальны;
- prefixed-запись (R, A, V, T, J) не должна продолжаться на следующую строку с отступом: одна запись занимает ровно одну строку; продолжение приписывается строке, начавшей запись, включая строки, уже несущие ошибку ID (синтаксис ID, дубликат) — перенос диагностируется всегда;
- prefixed-записи образуют плоский список: строка, сама являющаяся отступленной prefixed-записью (ведущий пробел + `- R2.1.`), — ошибка: иерархия выражается только многоуровневыми ID, не markdown-вложенностью; отступленный ребёнок всё же считается ребёнком в проверках группа/лист, но нигде больше не регистрируется — исправить отступ и перезапустить, чтобы структурные находки (дубликаты ID, предки) проявились на ставшей видимой записи;
- голый числовой литерал в любой секции, кроме Configuration и Examples, — ошибка. Литерал — число, начинающее слово: перед первой цифрой — начало строки или не-словесный символ (не буква, не цифра, не подчёркивание), в токен входят цифры, хвостовые словесные символы (`30s`, `3x`) и группы «десятичный разделитель + цифры» (`0,5`; `1.5`). Не литералы: числа внутри бэктиков (кодовые литералы — спаны `` `...` `` гасятся до сканирования); строки внутри fenced code block — строка, начинающаяся с `` ``` `` или `~~~` в нулевой колонке, тогглит состояние «в фенсе» (открывающий маркер может нести язык, например `` ```yaml ``): строки фенса пропускаются литерал-сканом, заголовки внутри фенса секцию не переключают; слова, начинающиеся с буквы (цифра за буквой/цифрой не начинает слово) — ID требований/примеров R1.2, A3, уровни верификации L0/L1/L2, версии v1.2, TLS1.2, включая хвостовую цифру цитируемого dotted-ID с последующим словом (R1.3 minutes, R2.2 states); число, приклеенное к предшествующему ALL-CAPS-слову — символ-разделитель включительно (TLS 1.2, UTF-8). Секция отслеживается по заголовкам `^#+ ` (внутренний заголовок задаёт текущую секцию по первому алфавитному слову заголовка; заголовки вида `## 3a. ...` задают пустую секцию — проза вне именованных секций сканируется с атрибутом «spec file»); строки заголовков сами не сканируются, внутри фенса заголовки не действуют. Проверка работает независимо от того, какие секции есть в файле. Сообщение: `<секция> section contains a bare numeric literal (<токен>) - forbidden outside Configuration and Examples; cite the name the spec keys the value under in Interface/Configuration` (для прозы вне именованных секций — `spec file contains ...`).

### Проверки index.md

- путь каждой строки индекса существует: сначала относительно корня git-репозитория (определяется через `git rev-parse --show-toplevel`; вне git-репозитория — родитель директории `specs/` либо сама директория индекса), затем относительно директории самого индекса;
- `Status` каждой строки — `draft` или `stable`;
- `Reference` — одна проверка по белому списку: идентификатор из строчных ASCII-букв и цифр, разделённых одиночными дефисами; всё прочее — заглавные буквы, не-ASCII алфавиты (кириллица и любой иной), иная пунктуация (underscore, точка), ведущие и хвостовые дефисы — ошибка `Reference must be a lowercase hyphen-separated ID: <ref>`; деления на «форму» и «язык», как у глоссария, здесь нет — белый список покрывает обе темы сразу. Уникален (собранные reference ID используются затем для проверки глоссариев).

### Проверки GLOSSARY.md

- форма term ID — структура `<reference>/<term>`;
- язык term ID — строго английский: не-ASCII буква (кириллица и любой иной алфавит) либо заглавная буква в любой из двух частей ID — ошибка с сообщением `term ID must be strictly English (<токен>)`; охват проверки — только строки GLOSSARY.md, язык term ID в текстах спек не сканируется (семантический проход — раздел `5` — и ревью); находка — ошибка, не предупреждение: вклад в код выхода `2`;
- строгий алфавитный порядок по полному ID;
- `Defined in` равен префиксу термина либо имеет форму «префикс (ID требований...)»;
- префикс разрешается против reference ID, собранных при линте индексов; когда те не собраны, проверка пропускается с предупреждением `warning:` (в stderr, с префиксом `speclint:`), дающим вклад в код выхода `1` при отсутствии ошибок.

### Вывод и коды выхода

Находки печатаются в stderr в формате `<файл>:<строка>: <сообщение>`. Предупреждения несут префикс `warning:` и печатаются в формате `speclint: <файл>: warning: <сообщение>`; единственное на сегодня предупреждение — пропуск проверки разрешения префиксов глоссария, когда собранных reference ID нет. Код выхода агрегируется по всем обработанным файлам как максимум:

- `0` — чисто;
- `1` — есть предупреждения, ошибок нет;
- `2` — есть ошибки линта; ошибка вызова (невалидная инвокация) — тоже `2`.

Известное ограничение (зафиксировано в шапке скрипта): линия-продолжение без отступа (lazy markdown) невидима построчному линту — правило одной строки остаётся отчасти проверкой ревью; отступленное продолжение ловится. Отслеживание фенсов — слепой тоггл по нулевой колонке: закрывающий маркер не сверяется с открывающим (длина, `` ``` ``/`~~~`), фенс с отступом не распознаётся, незакрытый фенс подавляет литерал-скан и переключение секций до конца файла.

## Ограничения и нецелевое использование

- Скилл — только для спек-документов и spec-driven изменений: не для README, не для общей документации (скилл `docs`), не для TLA+-спек, TLC-моделей и доказательств (скиллы `tla-plus`, `tlc-run`, `tlaps`).
- `speclint` — механический поднабор правил SKILL.md; семантика остаётся ручным проходом по разделу `5`. Линтом не проверяются: декларативность и однозначность формулировок, одна поведенческая фича на строку (составность требований), отсутствие объяснений в строках требований, связи Dependencies/Used by и их симметрия, язык спеки и англицизмы, статус в заголовке спек-файла, полнота Configuration, Verification-записи по существу. Уточнение по языку: проза спек и англицизмы линтом не проверяются, но язык term ID механически проверяется в строках GLOSSARY.md; в текстах спек (Definitions, тела требований) язык term ID не сканируется — семантический проход и ревью. Механическая языковая проверка ловит только заглавные ASCII-буквы и не-ASCII символы в частях term ID; прочая пунктуация printable-ASCII (пробел, точка, underscore и т.п.) в частях term ID линтом не диагностируется — полное правило набора символов (строчные ASCII-буквы, цифры, дефисы) остаётся предметом семантического прохода и ревью.
- Числа внутри бэктиков линтом пропускаются (механическое исключение для кодовых литералов), как и секции Configuration и Examples целиком и строки внутри fenced code blocks (фенсов) — это те места, где конкретные значения живут по построению; остающаяся за этими исключениями норма — цитировать имена, не значения (раздел `4`), — на остальной территории enforced механически, а её смысл проверяется семантическим проходом и ревью.
- В режиме директории линтятся все `.md` как кандидаты-спеки (включая README, DEVIATIONS.md и пр.) — проверки срабатывают только на строки, похожие на prefixed-записи, и на голые числовые литералы вне Configuration/Examples.
