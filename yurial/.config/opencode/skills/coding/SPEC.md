# Скилл coding Specification

Status: stable
Spec source of truth for: скилл `coding` — инструкция SKILL.md «Код: написание и ревью на любом языке» (написание и ревью кода на любом языке программирования)
Расхождение поведения скилла со спецификацией — либо пробел спецификации (правится она), либо баг скилла (правится SKILL.md); молчаливо терпить его нельзя.
Reference: coding

## Overview

Скилл `coding` регламентирует написание и ревью кода на любом языке программирования. Скилл — инструкции агенту: правила применяются агентом при написании и ревью кода. Правила описывают структуру, контракт и процесс написания кода — константность (R3), длину функции (R4), тестируемость (R5), тесты перед кодом (R6), покрытие тестами методов (R7), правило «Coverage gate» (R8), инкапсуляцию (R9), явные типы (R10), доменные алиасы типов (R11), контракт исключений (R12), соответствие спецификации (R13) и порядок «спецификация → тесты → код» (R14) — и не предписывают алгоритмы или архитектуру. Написание тестов входит в скилл и регламентируется правилами «Тесты перед кодом» (R6), «Покрытие тестами методов» (R7) и «Coverage gate» (R8); правило «Тестируемость» (R5) фиксирует требование проектирования кода под юнит-тесты. Базовый принцип применения всех правил — `coding/language-gate` (R2). Полный жизненный цикл задачи — от спецификации ожидаемого поведения до ревью готового кода — покрывается процессом применения (R15) и ревью-контрактом (R16); нарушения пары «код до тестов» наблюдаемы только `coding/live-observation` (R16.3). Скилл не несёт скриптов и механических проверок: линтеры, статические анализаторы, тестовые раннеры и инструменты измерения покрытия — вне скилла и запускаются своими средствами.

## Триггеры применения

Скилл активируется при написании нового кода на любом языке программирования (R1.1), при изменении существующего кода — правке, рефакторинге, расширении (R1.2) — и при ревью кода на любом языке: диффа, готового кода, предложений (R1.3); только для исходного кода и его ревью (R1.4). Скилл не применяется к спек-документам и spec-driven изменениям (скилл `spec`), проектной документации (скилл `docs`), TLA+-спекам, TLC-моделям и доказательствам (скиллы `tla-plus`, `tlc-run`, `tlaps`) (R1.5). Канонический текст триггеров — `description` frontmatter (Interface); нормы активации — R1.

## Scope

In:
- регламент написания нового кода, изменения существующего кода и ревью кода на любом языке (R1);
- языковой гейт применимости правил (R2);
- правила структуры, контракта и процесса кода (R3–R14);
- процесс применения, покрывающий полный жизненный цикл задачи (R15);
- чек-лист ревью и каталог анти-паттернов (R16, раздел «Анти-паттерны»);
- константы порогов `max-function-lines` и `coverage-threshold` (Configuration).

Out (non-goals):
- спек-документы и spec-driven изменения — скилл `spec`;
- проектная документация — скилл `docs`;
- TLA+-спеки, TLC-модели и доказательства — скиллы `tla-plus`, `tlc-run`, `tlaps`;
- выбор алгоритмов, паттернов проектирования и архитектуры;
- форматирование и стиль: отступы, кавычки, порядок импортов, длина строки, именование идентификаторов;
- механические проверки: линтеры, статические анализаторы, тестовые раннеры, инструменты измерения покрытия; скрипты и автоматизация.

## Definitions

| Term | Definition |
|---|---|
| `coding/language-gate` | Языковой гейт применимости: условие действия правил скилла в коде на конкретном языке — наличие предписываемого механизма или его эквивалента и идиоматичность применения; неприменимое правило пропускается молча (R2). |
| `coding/equivalent` | Эквивалент механизма: языковая конструкция, выполняющая в конкретном языке роль предписываемого правилом механизма; подбирается по языку. |
| `coding/whitelist` | Явный список исключений кода из-под `coverage-threshold`, ведущийся в проекте; каждое добавление требует эскалации и явного подтверждения пользователя (R8). |
| `coding/trivial-proxy` | Тривиальный метод-прокси: одна строка делегирования без собственной логики; теста не требует (R7). |
| `coding/red-stage` | Red-этап: состояние, в котором тесты, написанные до реализации, падают; нормальный этап порядка «спецификация → тесты → код» (R14). |
| `coding/live-observation` | Live-наблюдение: наблюдение за процессом написания кода в реальном времени; единственный способ проверки нарушений пары «код до тестов» (R16). |

## Configuration

| Name | Allowed values | Default | Effect |
|---|---|---|---|
| `max-function-lines` | `fixed` 50 строк | — | Порог правила «Длина функции» (R4): функция с телом длиннее порога разбивается на вспомогательные функции, исходная функция комбинирует их вызовами. |
| `coverage-threshold` | `fixed` 100% (строки и ветви) | — | Порог правила «Coverage gate» (R8): покрытие кода тестами поддерживается полным — по строкам и по ветвям (`branch`); изменение кода, снижающее покрытие ниже порога, запрещено. |

## Requirements

- R1. Триггеры применения (активация скилла):
- R1.1. Скилл применяется при написании нового кода на любом языке программирования.
- R1.2. Скилл применяется при изменении существующего кода: при правке, рефакторинге и расширении.
- R1.3. Скилл применяется при ревью кода на любом языке: ревью диффа, готового кода и предложений.
- R1.4. Скилл применяется только для исходного кода и его ревью.
- R1.5. Скилл не применяется к спек-документам и spec-driven изменениям (скилл `spec`), проектной документации (скилл `docs`), TLA+-спекам, TLC-моделям и доказательствам (скиллы `tla-plus`, `tlc-run`, `tlaps`).
- R2. Языковой гейт применимости (`coding/language-gate`):
- R2.1. Правило скилла действует в коде на конкретном языке только при наличии в языке предписываемого правилом механизма или его `coding/equivalent`.
- R2.2. Правило скилла действует только при идиоматичном применении: применение не противоречит общепринятым конвенциям языка.
- R2.3. `coding/equivalent` подбирается по языку.
- R2.4. Правило, неприменимое по `coding/language-gate`, пропускается молча.
- R2.5. Пропуск правила по `coding/language-gate` не является девиацией и не репортится как находка ревью.
- R2.6. Неприменимость правила в одном языке не отменяет действие правила в другом языке.
- R2.7. Имитация отсутствующего механизма хаками запрещена: обёртки-«константы», снятие константности (`const_cast` и аналоги), договорённости, не проверяемые языком.
- R2.8. Молчаливый пропуск неприменимых правил не распространяется на правило «Coverage gate» (R8).
- R3. Константность:
- R3.1. Переменная, метод или аргумент, которые могут быть константными, делаются константными: значение не изменяется после инициализации, метод не изменяет состояние объекта, аргумент не перезаписывается в теле функции.
- R3.2. Ради константности алгоритм и архитектура не меняются: сущность, которая не может быть константной без перестройки алгоритма, остаётся неконстантной, перестройка не выполняется.
- R3.3. Хаки константности запрещены: снятие константности, копирование данных ради видимой неизменяемости, `mutable`-поля, вводимые ради маркировки метода константным без логической константности.
- R4. Длина функции:
- R4.1. Функция, тело которой длиннее `max-function-lines`, разбивается на вспомогательные функции, а исходная функция комбинирует их вызовами.
- R4.2. Блок разбиения — осмысленный шаг алгоритма, имя вспомогательной функции отражает семантику шага.
- R4.3. Нарезка тела функции на произвольные фрагменты ради укладки в `max-function-lines` является нарушением правила.
- R4.4. Порог считается по строкам тела функции, границы тела определяются по синтаксису языка, для языков без скобок — по отступам и блокам.
- R4.5. Пустые строки и строки, содержащие только комментарии, в подсчёт тела не входят.
- R4.6. Строка, содержащая сигнатуру вместе с открывающей границей тела, в подсчёт не входит.
- R4.7. Докстринг в подсчёт тела не входит.
- R5. Тестируемость:
- R5.1. Каждый класс, метод и функция проектируются из расчёта, что для них пишутся юнит-тесты.
- R5.2. Юнит-тесты не совершают сетевых вызовов, не используют ожидание по времени и не работают с реальными базами данных.
- R5.3. Код допускает подмену зависимостей: внедрение зависимостей через аргументы конструктора или функции, интерфейсы и абстракции вместо конкретных типов.
- R5.4. Прямое обращение к глобальным синглтонам внешних систем — сетевых клиентов, баз данных, часов — внутри тестируемой логики запрещено, зависимость передаётся явно.
- R5.5. Код, работающий с текущим временем, получает время через аргументы: параметр-источник времени или момент времени.
- R5.6. Прямое чтение системных часов внутри логики запрещено.
- R6. Тесты перед кодом:
- R6.1. Перед написанием кода пишутся тесты на его публичный интерфейс: тест фиксирует контракт сущности до её реализации.
- R6.2. Тесты на публичный интерфейс обязательны и являются первичным контрактом сущности: они пишутся до реализации.
- R6.3. Правило распространяется на расширение существующего кода: на новое поведение публичного интерфейса тест пишется до кода этого поведения.
- R7. Покрытие тестами методов:
- R7.1. На каждый метод и каждую функцию пишется тест, проверяющий их поведение, включая приватные методы и функции.
- R7.2. Прямые тесты приватных методов — дополнительное требование покрытия: они дополняют тесты публичного контракта (R6), а не заменяют их.
- R7.3. Доступ к приватным методам в тестах выполняется по идиомам языка.
- R7.4. При отсутствии идиоматичного способа доступа к приватным методам действует `coding/language-gate`: требование тестов приватных методов пропускается молча.
- R7.5. `coding/trivial-proxy` теста не требует.
- R8. Coverage gate:
- R8.1. Покрытие кода тестами поддерживается равным `coverage-threshold`: полным по строкам и по ветвям (`branch`-покрытие).
- R8.2. Изменение кода, снижающее покрытие ниже `coverage-threshold` — строчное или `branch`, — запрещено.
- R8.3. Изменение кода сопровождается тестами, сохраняющими порог.
- R8.4. Код, легитимно непокрываемый тестами — точки входа и связывание, сгенерированный код, защитные ветви недостижимых состояний, `default`-ветви исчерпывающего сопоставления, — исключается из-под `coverage-threshold` только через `coding/whitelist`.
- R8.5. Каждое добавление в `coding/whitelist` требует эскалации и явного подтверждения пользователя.
- R8.6. Молчаливое исключение кода из-под покрытия запрещено и является находкой ревью.
- R8.7. Правило применяется, когда для языка или проекта доступен инструмент измерения покрытия с `branch`-метрикой, инструмент запускается своими средствами.
- R8.8. Недоступность инструмента измерения покрытия с `branch`-метрикой — блокер с эскалацией пользователю: тихий пропуск правила запрещён и является исключением из общего молчаливого пропуска неприменимых правил (R2.4, R2.5).
- R9. Инкапсуляция:
- R9.1. Реализация скрывается за публичным интерфейсом: наружу выставляется минимальный набор публичных членов, достаточный потребителям модуля, остальное приватно.
- R9.2. Знания, разделяемые между модулями и заголовочными файлами, минимизируются: внутренние типы и детали реализации не появляются в публичных сигнатурах без необходимости.
- R9.3. Заголовочный файл раскрывает только то, что нужно потребителю.
- R10. Явные типы:
- R10.1. Если переменной можно присвоить явный тип, тип присваивается явно.
- R10.2. Нетипизированные и «выводимые в никуда» переменные минимизируются.
- R10.3. Вывод типа (`auto`, `var`, `:=`) допустим, только когда тип однозначно читается из инициализатора в той же строке, иначе ставится явная аннотация.
- R10.4. Сигнатуры функций и методов — приоритетное место явных типов: параметры и возвращаемые значения типизируются явно там, где язык позволяет.
- R10.5. В языках, чьи конвенции предписывают вывод типов для локальных переменных, локальный вывод допустим по правилу читаемости (R10.3).
- R10.6. В языках, чьи конвенции предписывают вывод типов для локальных переменных, публичные сигнатуры типизируются явно.
- R11. Доменные алиасы типов:
- R11.1. Доменные сущности получают осмысленные алиасы типов вместо голых примитивов: объявление и сигнатура говорят о смысле значения, а не о носителе.
- R11.2. Алиас вводится для сущности домена, а не для каждого примитива: значение без доменного смысла алиаса не требует.
- R11.3. Именование алиаса следует конвенциям проекта.
- R11.4. Если язык различает алиас и новый несовместимый тип, выбор механизма определяется потребностью в несовместимости типов, а не формой правила.
- R12. Контракт исключений:
- R12.1. Контракт метода или функции указывает, какие исключения она может бросить, включая транзитивные — проброшенные из функций, вызываемых внутри.
- R12.2. Если исключений быть не должно, функция помечается `noexcept` или языковым эквивалентом.
- R12.3. Контракт фиксируется в сигнатуре, когда язык это позволяет, иначе — докстрингом или комментарием у сигнатуры.
- R12.4. В языках без исключений контракт ошибок фиксируется типом результата (`Result`, `error`).
- R12.5. Все пути ошибки видны в сигнатуре.
- R13. Соответствие спецификации:
- R13.1. Код соответствует спецификации проекта: поведение, границы и контракты реализации — как заявлено спецификацией.
- R13.2. Если для реализации требуется изменить спецификацию, пользователь уведомляется, и работа продолжается после его подтверждения.
- R13.3. Менять спецификацию без подтверждения пользователя запрещено.
- R13.4. Правило регламентирует отношение кода к спецификации, а не редактирование спек-документов: правка спецификации после подтверждения выполняется пользователем или скиллом `spec`.
- R14. Порядок «спецификация → тесты → код»:
- R14.1. При написании нового кода и изменении существующего соблюдается строгий порядок задач: спецификация → тесты → код.
- R14.2. Любое отклонение от порядка — код до тестов, тесты до спецификации — является нарушением правила.
- R14.3. Прежде чем писать любые тесты, существует спецификация, описывающая ожидаемое поведение.
- R14.4. Спецификации нет — сначала она создаётся или обновляется через spec-first flow скилла `spec`.
- R14.5. Изменение существующей спецификации допускается только с подтверждения пользователя (R13).
- R14.6. Реализация начинается только тогда, когда уже есть тесты, описывающие ожидаемое поведение (R6).
- R14.7. Падение тестов до реализации — нормальный `coding/red-stage`.
- R14.8. Порядок «интерфейсы без реализации → описания контрактов → тесты → код» согласован с настоящим правилом: контрактные описания — часть спецификационного этапа, до тестов.
- R14.9. На изменяемое поведение спецификация обновляется до тестов на него.
- R14.10. Тесты на изменение пишутся до кода изменения.
- R14.11. Правило «Тесты перед кодом» (R6) — частный случай настоящего правила, при расхождении приоритет у настоящего правила.
- R15. Процесс применения:
- R15.1. Процесс покрывает полный жизненный цикл задачи: от спецификации ожидаемого поведения до ревью готового кода.
- R15.2. Этапы жизненного цикла: спецификация, тесты, реализация, верификация (компиляция, тесты, покрытие), соответствие спецификации, ревью. Каждый этап жизненного цикла покрыт хотя бы одним правилом скилла.
- R15.3. Начинать процесс с этапа, следующего за спецификацией ожидаемого поведения, запрещено.
- R15.4. При написании нового кода и изменении существующего шаги выполняются по порядку: «Спецификация» → «Тесты на публичный интерфейс» → «Реализация» → «Компиляция, тесты, coverage» → «Соответствие спецификации».
- R15.5. На шаге «Спецификация» подтверждается существование спецификации, описывающей ожидаемое поведение, до написания тестов (R14).
- R15.6. На шаге «Спецификация» отсутствующая спецификация сначала создаётся или обновляется через spec-first flow скилла `spec`.
- R15.7. На шаге «Спецификация» изменение существующей спецификации выполняется только с подтверждения пользователя (R13).
- R15.8. На шаге «Тесты на публичный интерфейс» контракт сущности фиксируется тестами на её публичный интерфейс до реализации (R6).
- R15.9. На шаге «Тесты на публичный интерфейс» подтверждается, что код проектируется под юнит-тесты: зависимости подменяемые, время и внешние системы приходят через аргументы (R5).
- R15.10. На шаге «Тесты на публичный интерфейс» закладывается тест на каждый метод и функцию (R7).
- R15.11. На шаге «Реализация» правила кода (R3–R14) применяются к коду через `coding/language-gate`: неприменимое правило пропускается молча, хаки-имитации запрещены (R2).
- R15.12. На шаге «Компиляция, тесты, coverage» прогоняются компиляция, тесты и измерение покрытия своими средствами.
- R15.13. На шаге «Компиляция, тесты, coverage» покрытие удерживается на уровне `coverage-threshold` по строкам и ветвям (R8).
- R15.14. На шаге «Компиляция, тесты, coverage» при недоступности инструмента с `branch`-метрикой работа останавливается и эскалируется пользователю: это блокер, тихий пропуск запрещён (R8).
- R15.15. На шаге «Соответствие спецификации» поведение, границы и контракты реализации сверяются со спецификацией проекта (R13).
- R16. Ревью кода:
- R16.1. При ревью кода правила кода (R3–R14) проходят как чек-лист по каталогу анти-паттернов.
- R16.2. Каждая находка ревью репортится и не пропускается.
- R16.3. Нарушения пары «код до тестов» (R6, R14) проверяются только `coding/live-observation` процесса написания, при ревью готового кода по диффу они не репортятся как ненаблюдаемые.
- R16.4. По готовому коду репортится проверяемая форма нарушения правила «Тесты перед кодом»: тесты внутренних деталей вместо тестов публичного интерфейса.
- R17. Конвенции текста скилла:
- R17.1. Значения констант скилла фиксированы и согласованы с разделом Configuration настоящей спецификации.
- R17.2. В правилах и анти-паттернах скилла пороги цитируются по имени, без числовых литералов.
- R17.3. Примеры правила доменных алиасов в тексте скилла адаптируются под язык.
- R17.4. Примеры кода в тексте скилла иллюстративны — не вводят новых требований и не изменяют нормы.
- R17.5. Языковые формы обязательны в тексте скилла для правил, опирающихся на механизм языка с эквивалентами: гейт-эквиваленты и константность (A2), идиомы доступа к приватным методам в тестах (A7), инкапсуляция (A9), вывод типа `auto`/`var`/`:=` (R10.3), алиас/newtype (A11), контракт исключений (A12).
- R17.6. Перекрёстные ссылки в тексте скилла дают номер и имя правила.

## Examples

- A2. R2 subtree: `coding/equivalent` подбирается по языку — неизменяемость: `const`/`constexpr` в C++, привязка без `mut` в Rust, `val` в Kotlin, `let` в Swift, `readonly` в C#; запрет исключений: `noexcept` в C++, сигнатура без `throws` в Swift, контракт результата в Rust и Go; константность в Python — прямого механизма `const` нет, применяются эквиваленты (`typing.Final`, frozen-структуры) там, где это идиоматично, иначе правило пропускается; повсеместные явные типы локальных переменных там, где конвенции языка предписывают вывод типов, — неидиоматично.
- A4. R4 subtree: строка, содержащая сигнатуру вместе с открывающей границей тела (`void f() {`), не считается; пустые строки и строки только с комментариями не учитываются; докстринг не считается; для языков без скобок границы тела определяются по отступам и блокам.
- A7. R7 subtree: доступ к приватным методам в тестах — `friend` в C++, `#[cfg(test)]` в Rust, тесты в том же пакете или классе; идиоматичный способ доступа отсутствует — требование тестов приватных методов пропускается молча.
- A9. R9 subtree: языковые формы приватности — модификаторы доступа (`private`, `internal`) в C++/Java/C#, приватность по умолчанию и точечный `pub` в Rust, соглашение подчёркивания в Python, `private`- и `#`-поля в TypeScript.
- A10. R10 subtree: языки, чьи конвенции предписывают вывод типов для локальных переменных, — Kotlin и Swift: локально вывод допустим, когда тип однозначно читается из инициализатора в той же строке; публичные сигнатуры типизируются явно.
- A11. R11 subtree: C++ — `using TAddress = std::string;` и `TAddress address = "qwe";`; Rust — `type Address = String;`; Python — `type Address = str`; язык различает алиас и новый несовместимый тип — Python `NewType`, Rust newtype-обёртка — выбор механизма определяется потребностью в несовместимости типов.
- A12. R12 subtree: контракт в сигнатуре — checked-исключения Java, `throws` Swift; докстринг или комментарий у сигнатуры — Python, C++; контракт ошибок типом результата — Rust `Result`, Go `error`.
- A17. R17 subtree: формат перекрёстной ссылки в тексте скилла — номер и имя правила вместе, например «правило «Порядок» (3.12)»; пороги в правилах цитируются по имени — `max-function-lines`, `coverage-threshold` (R17.2).

## Анти-паттерны (чек-лист ревью)

Каталог находок ревью; каждая находка репортится, не пропускается (R16.2).

### Языковой гейт (R2)
- Применение правила, неприменимого к языку: требование константности в Python там, где нет идиоматичного эквивалента, `noexcept` в языке без механизма исключений.
- Хак, имитирующий отсутствующий механизм.

### Константность (R3)
- Неконстантная сущность, которая может быть константной.
- Перестройка алгоритма или архитектуры ради константности.
- Снятие константности.
- Копирование ради видимой неизменяемости.

### Длина функции (R4)
- Тело длиннее `max-function-lines`.
- Нарезка на бессмысленные фрагменты ради порога.
- Имя вспомогательной функции, не отражающее шаг.

### Тестируемость (R5)
- Прямое чтение системных часов в логике.
- Прямое обращение к сети, базе данных или глобальному синглтону в тестируемом коде.
- Юнит-тест с сетевым вызовом, ожиданием по времени или реальной базой данных.

### Тесты перед кодом (R6, R16.3, R16.4)
- Код, написанный раньше тестов на его публичный интерфейс, — находка, проверяемая только `coding/live-observation`; при ревью готового кода по диффу не репортится (ненаблюдаемо).
- По готовому коду репортится проверяемая форма: тесты внутренних деталей вместо тестов публичного интерфейса.

### Покрытие тестами методов (R7)
- Метод или функция без теста, не являющиеся `coding/trivial-proxy`, включая приватные.

### Coverage gate (R8)
- Падение покрытия ниже `coverage-threshold`.
- Непокрытая ветка.
- Код, исключённый из-под покрытия без записи в `coding/whitelist` или без явного подтверждения пользователя.
- Тихий пропуск правила при недоступном инструменте вместо эскалации пользователю.

### Инкапсуляция (R9)
- Публичный член без потребности потребителя.
- Внутренний тип в публичной сигнатуре.
- Детали реализации, раскрываемые заголовочным файлом.

### Явные типы (R10)
- Тип переменной, нечитаемый из строки объявления.
- Нетипизированный параметр или возвращаемое значение там, где язык позволяет явный тип.

### Доменные алиасы (R11)
- Голый примитив доменной сущности в сигнатуре.
- Алиас без смысла: переименование примитива ради формы.

### Контракт исключений (R12)
- Исключение, летящее из функции, чей контракт его не заявляет.
- Незаявленное транзитивное исключение.
- Отсутствие `noexcept` или эквивалента там, где исключений быть не должно.
- `noexcept` на функции, способной бросить.

### Соответствие спецификации (R13)
- Тихая правка спецификации.
- Расхождение кода со спецификацией без эскалации пользователю.

### Порядок «спецификация → тесты → код» (R14, R16.3)
- Тесты на поведение, отсутствующее в спецификации, включая тесты, написанные до создания спецификации.
- Код до тестов — нарушение, проверяемое `coding/live-observation`; при ревью готового кода по диффу не репортится (ненаблюдаемо).

## Usage constraints

- Скилл применяется только к написанию и ревью исходного кода (R1): не для спек-документов и spec-driven изменений (скилл `spec`), не для проектной документации (скилл `docs`), не для TLA+-спек, TLC-моделей и доказательств (скиллы `tla-plus`, `tlc-run`, `tlaps`).
- Правила не выбирают алгоритмы, паттерны проектирования и архитектуру: они применяются к коду в рамках выбранного решения, работающее решение не переписывается ради правила.
- Форматирование и стиль — вне скилла: отступы, кавычки, порядок импортов, длина строки, именование идентификаторов — территория инструментов форматирования, руководств по стилю и конвенций проекта.
- Конфликт правила с явной конвенцией проекта — эскалация пользователю, тихая победа одной из сторон запрещена.
- Механические проверки кода — вне скилла: линтеры, статические анализаторы, тестовые раннеры и инструменты измерения покрытия запускаются своими средствами; правила скилла — требования к коду и чек-лист ревью, а не инструмент.

## Error handling

- Блокер: недоступность инструмента измерения покрытия с `branch`-метрикой (R8.8, R15.14) — работа останавливается и эскалируется пользователю, тихий пропуск запрещён; единственное исключение из молчаливого пропуска неприменимых правил (R2.8).
- Эскалация с подтверждением пользователя: добавление в `coding/whitelist` (R8.5), правка спецификации проекта (R13.2, R13.3), конфликт правила с явной конвенцией проекта (Usage constraints).
- Молчаливый пропуск: неприменимое по `coding/language-gate` правило пропускается без репорта и не является находкой ревью (R2.4, R2.5), кроме правила «Coverage gate» (R2.8).

## Dependencies

- `spec` (скилл, не спек-документ): спецификация ожидаемого поведения создаётся и обновляется через spec-first flow скилла `spec` (R14.4, R15.6); правка спецификации после подтверждения пользователя выполняется пользователем или скиллом `spec` (R13.4).
