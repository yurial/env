# Скилл `coding`: спецификация

Status: draft
Spec source of truth for: скилл opencode `coding` — правила написания и ревью кода на любом языке программирования

Документ фиксирует функциональность скилла `coding`: назначение, условия применения, состав, контракт правил кода с языковым гейтом применимости, константы, анти-паттерны, границы применения. Скилл реализуется по настоящей спецификации: его SKILL.md следует ей и не противоречит. Расхождение поведения скилла со спецификацией — либо пробел спецификации (правится она), либо баг скилла (правится SKILL.md); молчаливо терпеть его нельзя. Каталог скилла в репозитории: `yurial/.config/opencode/skills/coding/`.

## Назначение

Скилл регламентирует написание и ревью кода на любом языке программирования. Правила описывают структуру, контракт и процесс написания кода — константность, длину функции, тестируемость, тесты перед кодом, покрытие тестами методов, coverage gate, инкапсуляцию, явность типов, доменные алиасы типов, контракт исключений, соответствие спецификации, порядок «спецификация → тесты → код» — и не предписывают алгоритмы или архитектуру.

Базовый принцип — языковой гейт применимости (language-applicability gate): каждое правило действует только при условии, что оно применимо к конкретному языку и идиоматично для него. Правило, чей механизм в языке отсутствует или чьё применение противоречит конвенциям языка, пропускается без шума; имитация отсутствующего механизма хаками запрещена.

Охватываемые области:

- языковой гейт применимости — общий принцип применения правил;
- правила кода: константность, длина функции, тестируемость, тесты перед кодом, покрытие тестами методов, coverage gate, инкапсуляция, явные типы, доменные алиасы типов, контракт исключений, соответствие спецификации, порядок «спецификация → тесты → код»;
- анти-паттерны — каталог находок ревью.

## Триггеры применения

Скилл применяется:

- при написании нового кода на любом языке программирования;
- при изменении существующего кода — правке, рефакторинге, расширении;
- при ревью кода на любом языке — ревью диффа, готового кода, предложений.

Запрещённые случаи: спек-документы и spec-driven изменения (скилл `spec`), проектная документация (скилл `docs`), TLA+-спеки, TLC-модели и доказательства (скиллы `tla-plus`, `tlc-run`, `tlaps`). Скилл применяется только к исходному коду и его ревью.

## Компоненты скилла

### SKILL.md

Инструкция скилла (загружается при активации). Состав: назначение, языковой гейт применимости, константы (раздел Configuration — согласован с разделом Configuration настоящей спецификации), правила кода с языковыми формами и примерами, процесс применения, анти-паттерны, границы применения. Процесс применения задаёт порядок шагов при написании и изменении кода — спецификация → тесты на публичный интерфейс → реализация → компиляция/тесты/coverage → соответствие спецификации; ветка ревью — проход правил кода как чек-лист анти-паттернов. Frontmatter: `name: coding`; `description` перечисляет триггеры применения (написание нового кода, изменение существующего кода, ревью кода — на любом языке) и исключения (спеки, документация, TLA+-артефакты). Скилл не несёт скриптов и механических проверок: правила применяются агентом при написании и ревью кода; линтеры и статические анализаторы языка — вне скилла.

## Контракты

Правила, которые скилл накладывает на написание и ревью кода.

### Полнота жизненного цикла

- Задаваемый скиллом процесс написания и изменения кода покрывает полный жизненный цикл задачи: от спецификации ожидаемого поведения до ревью готового кода.
- Каждый этап жизненного цикла — спецификация, тесты, реализация, верификация (компиляция, тесты, покрытие), соответствие спецификации, ревью — покрыт хотя бы одним правилом скилла.
- Процесс не может начинаться с этапа, следующего за спецификацией ожидаемого поведения: закрепление начала цепочки позже этапа спецификации запрещено.

### Языковой гейт применимости

- Правило применяется к коду на языке при одновременном соблюдении условий: в языке есть предписываемый правилом механизм или его эквивалент; применение идиоматично — не противоречит общепринятым конвенциям языка.
- Эквивалент механизма подбирается по языку: неизменяемость — `const`/`constexpr` в C++, привязка без `mut` в Rust, `val` в Kotlin, `let` в Swift, `readonly` в C#; запрет исключений — `noexcept` в C++, сигнатура без `throws` в Swift, контракт результата в Rust и Go.
- Правило, неприменимое по гейту, пропускается молча: пропуск — не девиация и не находка ревью. Примеры: константность в Python — прямого механизма `const` нет, применяются эквиваленты (`typing.Final`, frozen-структуры) там, где это идиоматично, иначе правило пропускается; повсеместные явные типы локальных переменных там, где конвенции языка предписывают вывод типов, — неидиоматично.
- Исключение из молчаливого пропуска — правило «Coverage gate»: недоступность инструмента измерения покрытия с branch-метрикой не даёт пропуска правила — это блокер с эскалацией пользователю.
- Гейт не ослабляет правило там, где механизм есть: неприменимость в одном языке не отменяет правило в другом.
- Имитация отсутствующего механизма хаками запрещена: обёртки-«константы», снятие константности (`const_cast` и аналоги), договорённости, которые язык не проверяет, — не применяются.

### Правила кода

#### Константность

- Если переменная, метод или аргумент может быть константным — он делается константным: значение не изменяется после инициализации; метод не изменяет состояние объекта; аргумент не перезаписывается в теле функции.
- Ради константности не меняются алгоритм и архитектура: если сущность не может быть константной без перестройки алгоритма, она остаётся неконстантной; перестройка не выполняется.
- Хаки константности запрещены: снятие константности; копирование данных ради видимой неизменяемости; `mutable`-поля, вводимые ради маркировки метода константным без логической константности.

#### Длина функции

- Функция, тело которой длиннее `max-function-lines`, разбивается на отдельные блоки — вспомогательные функции, — а исходная функция комбинирует их вызовами.
- Блок — осмысленный шаг алгоритма; имя вспомогательной функции отражает семантику шага. Нарезка тела на произвольные фрагменты ради укладки в порог — нарушение правила.
- Порог считается по строкам тела функции. Границы тела определяются по синтаксису языка; для языков без скобок — по отступам/блокам. Строка, содержащая сигнатуру вместе с открывающей границей тела (например, `void f() {`), не считается. Пустые строки и строки, содержащие только комментарии, не учитываются; докстринг не считается.

#### Тестируемость

- Каждый класс, метод и функция проектируются из расчёта, что для них пишутся юнит-тесты.
- Юнит-тесты не совершают сетевых вызовов, не используют ожидание по времени и не работают с реальными базами данных; код обязан допускать подмену зависимостей: внедрение зависимостей через аргументы конструктора или функции, интерфейсы и абстракции вместо конкретных типов.
- Прямое обращение к глобальным синглтонам внешних систем — сетевых клиентов, баз данных, часов — внутри тестируемой логики запрещено; зависимость передаётся явно.
- Код, работающий с текущим временем, получает время через аргументы — параметр-источник времени или момент времени; прямое чтение системных часов внутри логики запрещено.
- Написание тестов входит в скилл и регламентируется правилами «Тесты перед кодом», «Покрытие тестами методов» и «Coverage gate»; настоящее правило фиксирует требование тестируемости — код проектируется под юнит-тесты.

#### Тесты перед кодом

- Перед написанием кода пишутся тесты на его публичный интерфейс: тест фиксирует контракт сущности до её реализации.
- Тесты на публичный интерфейс — обязательны и являются первичным контрактом сущности: они пишутся до реализации. Прямые тесты приватных методов — дополнительное требование покрытия (правило «Покрытие тестами методов»): они дополняют тесты публичного контракта, а не заменяют их.
- Правило распространяется и на расширение существующего кода: на новое поведение публичного интерфейса тест пишется до кода этого поведения.
- Правило регламентирует пару «тесты → код» и является частным случаем правила «Порядок: спецификация → тесты → код»; при расхождении приоритет у правила «Порядок».

#### Покрытие тестами методов

- На каждый метод и функцию пишется тест, проверяющий их поведение, — включая приватные методы и функции.
- Тесты на публичный интерфейс — обязательны и являются первичным контрактом (правило «Тесты перед кодом»); прямые тесты приватных методов — дополнительное требование покрытия: они дополняют тесты публичного контракта, а не заменяют их.
- Доступ к приватным методам в тестах выполняется по идиомам языка: `friend` в C++, `#[cfg(test)]` в Rust, тесты в том же пакете или классе и т. п.; если идиоматичный способ доступа отсутствует, действует языковой гейт — требование тестов приватных методов пропускается молча.
- Исключение — тривиальные методы-прокси: одна строка делегирования без собственной логики; такой метод теста не требует.

#### Coverage gate

- Покрытие кода тестами поддерживается равным `coverage-threshold`: полным, и по строкам, и по ветвям (branch-покрытие).
- Изменение кода, снижающее покрытие ниже `coverage-threshold` — строчное или branch, — запрещено: изменение сопровождается тестами, сохраняющими порог.
- Код, легитимно непокрываемый тестами — точки входа и wiring, сгенерированный код, defensive-ветки недостижимых состояний, default-ветки exhaustive-match, — может быть исключён из-под `coverage-threshold` только через whitelist: явный список исключений, ведущийся в проекте.
- Каждое добавление в whitelist требует эскалации и явного подтверждения пользователя; молчаливое исключение кода из-под покрытия запрещено и является находкой ревью.
- Языковой гейт: gate применяется, когда для языка или проекта доступен инструмент измерения coverage с branch-метрикой; инструмент запускается своими средствами.
- Недоступность инструмента — блокер с эскалацией пользователю: тихий пропуск правила запрещён и является исключением из общего молчаливого пропуска неприменимых правил.

#### Инкапсуляция

- Реализация скрывается за публичным интерфейсом: наружу выставляется минимальный набор публичных членов, достаточный потребителям модуля; остальное приватно.
- Минимизируются знания, разделяемые между модулями и заголовочными файлами: внутренние типы и детали реализации не появляются в публичных сигнатурах без необходимости; заголовочный файл раскрывает только то, что нужно потребителю.
- Языковые формы: модификаторы доступа (`private`, `internal`) в C++/Java/C#; приватность по умолчанию и точечный `pub` в Rust; соглашение подчёркивания в Python; `private`- и `#`-поля в TypeScript.

#### Явные типы

- Если переменной можно присвоить явный тип — тип присваивается явно.
- Нетипизированные и «выводимые в никуда» переменные минимизируются: вывод типа (`auto`, `var`, `:=`) допустим, только когда тип однозначно читается из инициализатора в той же строке; иначе ставится явная аннотация.
- Сигнатуры функций и методов — приоритетное место явных типов: параметры и возвращаемые значения типизируются явно там, где язык позволяет.
- Языковой гейт ослабляет правило в языках, чьи конвенции предписывают вывод типов для локальных переменных (Kotlin, Swift): локально вывод допустим по правилу читаемости выше; публичные сигнатуры типизируются явно.

#### Доменные алиасы типов

- Доменные сущности получают осмысленные алиасы типов вместо голых примитивов: объявление и сигнатура говорят о смысле значения, а не о носителе.
- Примеры адаптируются под язык:

```cpp
using TAddress = std::string;
TAddress address = "qwe";
```

```rust
type Address = String;
```

```python
type Address = str
```

- Алиас вводится для сущности домена, а не для каждого примитива: значение без доменного смысла алиаса не требует; именование алиаса следует конвенциям проекта.
- Если язык различает алиас и новый несовместимый тип (Python `NewType`, Rust newtype-обёртка), выбор механизма определяется потребностью в несовместимости типов, а не формой правила.

#### Контракт исключений

- Контракт метода или функции указывает, какие исключения она может бросить, включая транзитивные — проброшенные из функций, вызываемых внутри.
- Если исключений быть не должно, функция помечается `noexcept` или языковым эквивалентом.
- Контракт фиксируется в сигнатуре, когда язык это позволяет (checked-исключения Java, `throws` Swift); иначе — докстрингом или комментарием у сигнатуры (Python, C++).
- Языковой гейт для языков без исключений (Rust, Go): контракт ошибок фиксируется типом результата (`Result`, `error`); правило требует полноты этого контракта — все пути ошибки видны в сигнатуре.

#### Соответствие спецификации

- Код соответствует спецификации проекта: поведение, границы и контракты реализации — как заявлено спецификацией.
- Если для реализации требуется изменить спецификацию, пользователь уведомляется, и работа продолжается после его подтверждения; менять спецификацию без подтверждения пользователя запрещено.
- Правило регламентирует отношение кода к спецификации, а не редактирование спек-документов: правка спецификации после подтверждения выполняется пользователем или своим процессом (скилл `spec`).

#### Порядок: спецификация → тесты → код

- Строгий порядок задач при написании нового кода и изменении существующего: спецификация → тесты → код. Любое отклонение — код до тестов, тесты до спецификации — нарушение правила.
- Спецификация до тестов: прежде чем писать любые тесты, существует спецификация, описывающая ожидаемое поведение. Спеки нет — сначала она создаётся или обновляется (spec-first flow, скилл `spec`); изменение существующей спецификации — только с подтверждения пользователя (правило «Соответствие спецификации»).
- Тесты до кода: реализация начинается только тогда, когда уже есть тесты, описывающие ожидаемое поведение (правило «Тесты перед кодом»); тесты до реализации падают — это нормальный red-этап.
- Порядок «интерфейсы без реализации → описания контрактов → тесты → код» согласован с настоящим правилом: контрактные описания — часть спецификационного этапа, до тестов.
- Правило распространяется и на изменение существующего кода — правку, рефакторинг, расширение: на изменяемое поведение спецификация обновляется до тестов на него, тесты пишутся до кода изменения.
- Правило «Тесты перед кодом» — частный случай настоящего правила (пара «тесты → код»); при расхождении приоритет у настоящего правила.

### Анти-паттерны

Каталог находок ревью; каждая находка репортится, не пропускается.

- Языковой гейт: применение правила, неприменимого к языку (требование константности в Python там, где нет идиоматичного эквивалента, `noexcept` в языке без механизма исключений); хак, имитирующий отсутствующий механизм.
- Константность: неконстантная сущность, которая может быть константной; перестройка алгоритма или архитектуры ради константности; снятие константности; копирование ради видимой неизменяемости.
- Длина функции: тело длиннее `max-function-lines`; нарезка на бессмысленные фрагменты ради порога; имя вспомогательной функции, не отражающее шаг.
- Тестируемость: прямое чтение системных часов в логике; прямое обращение к сети, базе данных или глобальному синглтону в тестируемом коде; юнит-тест с сетевым вызовом, ожиданием по времени или реальной базой данных.
- Тесты перед кодом: код, написанный раньше тестов на его публичный интерфейс, — находка, проверяемая только live-наблюдением процесса написания; при ревью готового кода по диффу не репортится (ненаблюдаемо); по готовому коду репортится проверяемая форма — тесты внутренних деталей вместо тестов публичного интерфейса.
- Покрытие тестами методов: метод или функция без теста, не являющиеся тривиальным прокси, — включая приватные.
- Coverage gate: падение покрытия ниже `coverage-threshold`; непокрытая ветка; код, исключённый из-под покрытия без записи в whitelist или без явного подтверждения пользователя; тихий пропуск gate при недоступном инструменте вместо эскалации пользователю.
- Инкапсуляция: публичный член без потребности потребителя; внутренний тип в публичной сигнатуре; детали реализации, раскрываемые заголовочным файлом.
- Явные типы: тип переменной, нечитаемый из строки объявления; нетипизированный параметр или возвращаемое значение там, где язык позволяет явный тип.
- Доменные алиасы: голый примитив доменной сущности в сигнатуре; алиас без смысла — переименование примитива ради формы.
- Контракт исключений: исключение, летящее из функции, чей контракт его не заявляет; незаявленное транзитивное исключение; отсутствие `noexcept` или эквивалента там, где исключений быть не должно; `noexcept` на функции, способной бросить.
- Соответствие спецификации: тихая правка спецификации; расхождение кода со спецификацией без эскалации пользователю.
- Порядок «спецификация → тесты → код»: тесты на поведение, отсутствующее в спецификации, — включая тесты, написанные до создания спецификации; код до тестов — нарушение порядка, проверяемое live-наблюдением процесса написания (как в правиле «Тесты перед кодом»), при ревью готового кода по диффу не репортится (ненаблюдаемо).

## Configuration

| Name | Allowed values | Default | Effect |
|---|---|---|---|
| `max-function-lines` | `fixed` `50` строк | — | Порог правила «Длина функции»: функция с телом длиннее порога разбивается на вспомогательные функции, исходная функция комбинирует их вызовами |
| `coverage-threshold` | `fixed` `100%` (строки и ветви) | — | Порог правила «Coverage gate»: покрытие кода тестами поддерживается полным — по строкам и по ветвям (branch); изменение кода, снижающее покрытие ниже порога, запрещено |

## Ограничения и нецелевое использование

- Скилл — только для написания и ревью исходного кода: не для спек-документов и spec-driven изменений (скилл `spec`), не для проектной документации (скилл `docs`), не для TLA+-спек, TLC-моделей и доказательств (скиллы `tla-plus`, `tlc-run`, `tlaps`).
- Правила не выбирают алгоритмы, паттерны проектирования и архитектуру: они применяются к коду в рамках выбранного решения; работающее решение не переписывается ради правила.
- Форматирование и стиль — вне скилла: отступы, кавычки, порядок импортов, длина строки, именование идентификаторов — территория форматтеров, стайл-гайдов и конвенций проекта.
- Конфликт правила с явной конвенцией проекта — эскалация пользователю; тихая победа одной из сторон запрещена.
- Механические проверки кода — вне скилла: линтеры, статические анализаторы, тестовые раннеры и инструменты измерения покрытия запускаются своими средствами; правила скилла — требования к коду и чек-лист ревью, а не инструмент.
