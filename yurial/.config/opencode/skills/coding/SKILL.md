# Код: написание и ревью на любом языке

Скилл регламентирует написание и ревью кода на любом языке программирования.
Правила описывают структуру, контракт и процесс написания кода — константность,
длину функции, тестируемость, тесты перед кодом, покрытие тестами методов,
coverage gate, инкапсуляцию, явность типов, доменные алиасы типов, контракт
исключений, соответствие спецификации, порядок «спецификация → тесты → код» —
и не предписывают алгоритмы или архитектуру.

Скилл — инструкции агенту: правила применяются тобой при написании и ревью
кода. Скилл не несёт скриптов и механических проверок; линтеры, статические
анализаторы, тестовые раннеры и инструменты измерения покрытия — вне скилла и
запускаются своими средствами.

Базовый принцип применения правил — языковой гейт применимости (раздел 1).

## 1. Языковой гейт применимости

Каждое правило действует в коде на конкретном языке только при одновременном
соблюдении двух условий:

1. В языке есть предписываемый правилом механизм или его эквивалент.
2. Применение идиоматично — не противоречит общепринятым конвенциям языка.

Эквивалент механизма подбирается по языку:

- неизменяемость — `const`/`constexpr` в C++, привязка без `mut` в Rust,
  `val` в Kotlin, `let` в Swift, `readonly` в C#;
- запрет исключений — `noexcept` в C++, сигнатура без `throws` в Swift,
  контракт результата в Rust и Go.

Правило, неприменимое по гейту, пропускается молча: пропуск — не девиация и не
находка ревью. Примеры: константность в Python — прямого механизма `const`
нет, применяются эквиваленты (`typing.Final`, frozen-структуры) там, где это
идиоматично, иначе правило пропускается; повсеместные явные типы локальных
переменных там, где конвенции языка предписывают вывод типов, —
неидиоматично.

Исключение из молчаливого пропуска — правило «Coverage gate» (раздел 3.6):
недоступность инструмента измерения покрытия с branch-метрикой не даёт
пропуска правила — это блокер с эскалацией пользователю.

Гейт не ослабляет правило там, где механизм есть: неприменимость правила в
одном языке не отменяет его в другом.

Имитация отсутствующего механизма хаками запрещена: обёртки-«константы»,
снятие константности (`const_cast` и аналоги), договорённости, которые язык
не проверяет, — не применяются.

## 2. Configuration

- `max-function-lines` — `fixed` 50 строк. Порог правила «Длина функции»
  (раздел 3.2): функция с телом длиннее порога разбивается на вспомогательные
  функции, исходная функция комбинирует их вызовами.
- `coverage-threshold` — `fixed` 100% (строки и ветви). Порог правила
  «Coverage gate» (раздел 3.6): покрытие кода тестами поддерживается полным —
  по строкам и по ветвям (branch); изменение кода, снижающее покрытие ниже
  порога, запрещено.

Значения фиксированы и согласованы с разделом Configuration спецификации
скилла `coding`. В правилах и анти-паттернах ниже пороги цитируются
по имени, без числовых литералов.

## 3. Правила кода

### 3.1. Константность

- Если переменная, метод или аргумент может быть константным — он делается
  константным: значение не изменяется после инициализации; метод не изменяет
  состояние объекта; аргумент не перезаписывается в теле функции.
- Ради константности не меняются алгоритм и архитектура: если сущность не
  может быть константной без перестройки алгоритма, она остаётся
  неконстантной; перестройка не выполняется.
- Хаки константности запрещены: снятие константности; копирование данных ради
  видимой неизменяемости; `mutable`-поля, вводимые ради маркировки метода
  константным без логической константности.

### 3.2. Длина функции

- Функция, тело которой длиннее `max-function-lines`, разбивается на отдельные
  блоки — вспомогательные функции, — а исходная функция комбинирует их
  вызовами.
- Блок — осмысленный шаг алгоритма; имя вспомогательной функции отражает
  семантику шага. Нарезка тела на произвольные фрагменты ради укладки в порог
  — нарушение правила.
- Порог считается по строкам тела функции. Границы тела определяются по
  синтаксису языка; для языков без скобок — по отступам/блокам. Строка,
  содержащая сигнатуру вместе с открывающей границей тела (например,
  `void f() {`), не считается. Пустые строки и строки, содержащие только
  комментарии, не учитываются; докстринг не считается.

### 3.3. Тестируемость

- Каждый класс, метод и функция проектируются из расчёта, что для них пишутся
  юнит-тесты.
- Юнит-тесты не совершают сетевых вызовов, не используют ожидание по времени
  и не работают с реальными базами данных; код обязан допускать подмену
  зависимостей: внедрение зависимостей через аргументы конструктора или
  функции, интерфейсы и абстракции вместо конкретных типов.
- Прямое обращение к глобальным синглтонам внешних систем — сетевых клиентов,
  баз данных, часов — внутри тестируемой логики запрещено; зависимость
  передаётся явно.
- Код, работающий с текущим временем, получает время через аргументы —
  параметр-источник времени или момент времени; прямое чтение системных часов
  внутри логики запрещено.
- Написание тестов входит в скилл и регламентируется правилами «Тесты перед
  кодом» (3.4), «Покрытие тестами методов» (3.5) и «Coverage gate» (3.6);
  настоящее правило фиксирует требование тестируемости — код проектируется
  под юнит-тесты.

### 3.4. Тесты перед кодом

- Перед написанием кода пишутся тесты на его публичный интерфейс: тест
  фиксирует контракт сущности до её реализации.
- Тесты на публичный интерфейс — обязательны и являются первичным контрактом
  сущности: они пишутся до реализации. Прямые тесты приватных методов —
  дополнительное требование покрытия (правило «Покрытие тестами методов»,
  3.5): они дополняют тесты публичного контракта, а не заменяют их.
- Правило распространяется и на расширение существующего кода: на новое
  поведение публичного интерфейса тест пишется до кода этого поведения.

### 3.5. Покрытие тестами методов

- На каждый метод и функцию пишется тест, проверяющий их поведение, —
  включая приватные методы и функции.
- Тесты на публичный интерфейс — обязательны и являются первичным контрактом
  (правило «Тесты перед кодом», 3.4); прямые тесты приватных методов —
  дополнительное требование покрытия: они дополняют тесты публичного
  контракта, а не заменяют их.
- Доступ к приватным методам в тестах выполняется по идиомам языка: `friend`
  в C++, `#[cfg(test)]` в Rust, тесты в том же пакете или классе и т. п.;
  если идиоматичный способ доступа отсутствует, действует языковой гейт —
  требование тестов приватных методов пропускается молча.
- Исключение — тривиальные методы-прокси: одна строка делегирования без
  собственной логики; такой метод теста не требует.

### 3.6. Coverage gate

- Покрытие кода тестами поддерживается равным `coverage-threshold`: полным,
  и по строкам, и по ветвям (branch-покрытие).
- Изменение кода, снижающее покрытие ниже `coverage-threshold` — строчное или
  branch, — запрещено: изменение сопровождается тестами, сохраняющими порог.
- Код, легитимно непокрываемый тестами — точки входа и wiring,
  сгенерированный код, defensive-ветки недостижимых состояний, default-ветки
  exhaustive-match, — может быть исключён из-под `coverage-threshold` только
  через whitelist: явный список исключений, ведущийся в проекте.
- Каждое добавление в whitelist требует эскалации и явного подтверждения
  пользователя; молчаливое исключение кода из-под покрытия запрещено и
  является находкой ревью.
- Языковой гейт: gate применяется, когда для языка или проекта доступен
  инструмент измерения coverage с branch-метрикой; инструмент запускается
  своими средствами.
- Недоступность инструмента — блокер с эскалацией пользователю: тихий пропуск
  правила запрещён и является исключением из общего молчаливого пропуска
  неприменимых правил (раздел 1).

### 3.7. Инкапсуляция

- Реализация скрывается за публичным интерфейсом: наружу выставляется
  минимальный набор публичных членов, достаточный потребителям модуля;
  остальное приватно.
- Минимизируются знания, разделяемые между модулями и заголовочными файлами:
  внутренние типы и детали реализации не появляются в публичных сигнатурах
  без необходимости; заголовочный файл раскрывает только то, что нужно
  потребителю.
- Языковые формы: модификаторы доступа (`private`, `internal`) в
  C++/Java/C#; приватность по умолчанию и точечный `pub` в Rust; соглашение
  подчёркивания в Python; `private`- и `#`-поля в TypeScript.

### 3.8. Явные типы

- Если переменной можно присвоить явный тип — тип присваивается явно.
- Нетипизированные и «выводимые в никуда» переменные минимизируются: вывод
  типа (`auto`, `var`, `:=`) допустим, только когда тип однозначно читается
  из инициализатора в той же строке; иначе ставится явная аннотация.
- Сигнатуры функций и методов — приоритетное место явных типов: параметры и
  возвращаемые значения типизируются явно там, где язык позволяет.
- Языковой гейт ослабляет правило в языках, чьи конвенции предписывают вывод
  типов для локальных переменных (Kotlin, Swift): локально вывод допустим по
  правилу читаемости выше; публичные сигнатуры типизируются явно.

### 3.9. Доменные алиасы типов

- Доменные сущности получают осмысленные алиасы типов вместо голых
  примитивов: объявление и сигнатура говорят о смысле значения, а не о
  носителе.
- Примеры адаптируются под язык:

```cpp
using TAddress = std::string;
TAddress address = "qwe";
```

```rust
type Address = String;
```

```python
type Address = str
```

- Алиас вводится для сущности домена, а не для каждого примитива: значение
  без доменного смысла алиаса не требует; именование алиаса следует
  конвенциям проекта.
- Если язык различает алиас и новый несовместимый тип (Python `NewType`, Rust
  newtype-обёртка), выбор механизма определяется потребностью в
  несовместимости типов, а не формой правила.

### 3.10. Контракт исключений

- Контракт метода или функции указывает, какие исключения она может бросить,
  включая транзитивные — проброшенные из функций, вызываемых внутри.
- Если исключений быть не должно, функция помечается `noexcept` или языковым
  эквивалентом.
- Контракт фиксируется в сигнатуре, когда язык это позволяет
  (checked-исключения Java, `throws` Swift); иначе — докстрингом или
  комментарием у сигнатуры (Python, C++).
- Языковой гейт для языков без исключений (Rust, Go): контракт ошибок
  фиксируется типом результата (`Result`, `error`); правило требует полноты
  этого контракта — все пути ошибки видны в сигнатуре.

### 3.11. Соответствие спецификации

- Код соответствует спецификации проекта: поведение, границы и контракты
  реализации — как заявлено спецификацией.
- Если для реализации требуется изменить спецификацию, пользователь
  уведомляется, и работа продолжается после его подтверждения; менять
  спецификацию без подтверждения пользователя запрещено.
- Правило регламентирует отношение кода к спецификации, а не редактирование
  спек-документов: правка спецификации после подтверждения выполняется
  пользователем или своим процессом (скилл `spec`).

### 3.12. Порядок: спецификация → тесты → код

- Строгий порядок задач при написании кода: спецификация → тесты → код. Любое
  отклонение — код до тестов, тесты до спецификации — нарушение правила.
- Спецификация до тестов: прежде чем писать любые тесты, существует
  спецификация, описывающая ожидаемое поведение. Спеки нет — сначала она
  создаётся или обновляется (spec-first flow, скилл `spec`); изменение
  существующей спецификации — только с подтверждения пользователя (правило
  «Соответствие спецификации», 3.11).
- Тесты до кода: реализация начинается только тогда, когда уже есть тесты,
  описывающие ожидаемое поведение (правило «Тесты перед кодом», 3.4); тесты до
  реализации падают — это нормальный red-этап.
- Порядок «интерфейсы без реализации → описания контрактов → тесты → код»
  согласован с настоящим правилом: контрактные описания — часть
  спецификационного этапа, до тестов.

## 4. Процесс применения

При написании нового кода и изменении существующего выполняй шаги по
порядку:

1. **Спецификация** — до тестов (правило 3.12): убедись, что существует
   спецификация, описывающая ожидаемое поведение; спеки нет — сначала она
   создаётся или обновляется (spec-first flow, скилл `spec`), изменение
   существующей спецификации — только с подтверждения пользователя (3.11).
2. **Тесты на публичный интерфейс** — до реализации (правила 3.3-3.5):
   зафиксируй контракт сущности тестами на её публичный интерфейс; убедись,
   что код проектируется под юнит-тесты — зависимости подменяемые, время и
   внешние системы приходят через аргументы; заложи тест на каждый метод и
   функцию.
3. **Реализация** — примени правила 3.1-3.12 к коду через языковой гейт
   раздела 1: неприменимое правило пропускается молча, хаки-имитации
   запрещены.
4. **Компиляция, тесты, coverage** — прогони компиляцию, тесты и измерение
   покрытия своими средствами; coverage gate (3.6): покрытие удерживается на
   уровне `coverage-threshold` по строкам и ветвям. Инструмент с
   branch-метрикой недоступен — останови работу и эскалируй пользователю:
   это блокер, тихий пропуск запрещён.
5. **Соответствие спецификации** (3.11) — сверь поведение, границы и
   контракты реализации со спецификацией проекта. Для реализации требуется
   правка спецификации — уведоми пользователя и продолжай после его
   подтверждения; правка выполняется пользователем или скиллом `spec`.

При ревью кода проходи правила 3.1-3.12 как чек-лист по разделу 5; каждая
находка репортится, не пропускается.

## 5. Анти-паттерны (чек-лист ревью)

Каталог находок ревью; каждая находка репортится, не пропускается.

- Языковой гейт: применение правила, неприменимого к языку (требование
  константности в Python там, где нет идиоматичного эквивалента, `noexcept`
  в языке без механизма исключений); хак, имитирующий отсутствующий
  механизм.
- Константность: неконстантная сущность, которая может быть константной;
  перестройка алгоритма или архитектуры ради константности; снятие
  константности; копирование ради видимой неизменяемости.
- Длина функции: тело длиннее `max-function-lines`; нарезка на бессмысленные
  фрагменты ради порога; имя вспомогательной функции, не отражающее шаг.
- Тестируемость: прямое чтение системных часов в логике; прямое обращение к
  сети, базе данных или глобальному синглтону в тестируемом коде; юнит-тест с
  сетевым вызовом, ожиданием по времени или реальной базой данных.
- Тесты перед кодом: код, написанный раньше тестов на его публичный
  интерфейс, — находка, проверяемая только live-наблюдением процесса
  написания; при ревью готового кода по диффу не репортится (ненаблюдаемо);
  по готовому коду репортится проверяемая форма — тесты внутренних деталей
  вместо тестов публичного интерфейса.
- Покрытие тестами методов: метод или функция без теста, не являющиеся
  тривиальным прокси, — включая приватные.
- Coverage gate: падение покрытия ниже `coverage-threshold`; непокрытая
  ветка; код, исключённый из-под покрытия без записи в whitelist или без
  явного подтверждения пользователя; тихий пропуск gate при недоступном
  инструменте вместо эскалации пользователю.
- Инкапсуляция: публичный член без потребности потребителя; внутренний тип в
  публичной сигнатуре; детали реализации, раскрываемые заголовочным файлом.
- Явные типы: тип переменной, нечитаемый из строки объявления; нетипизированный
  параметр или возвращаемое значение там, где язык позволяет явный тип.
- Доменные алиасы: голый примитив доменной сущности в сигнатуре; алиас без
  смысла — переименование примитива ради формы.
- Контракт исключений: исключение, летящее из функции, чей контракт его не
  заявляет; незаявленное транзитивное исключение; отсутствие `noexcept` или
  эквивалента там, где исключений быть не должно; `noexcept` на функции,
  способной бросить.
- Соответствие спецификации: тихая правка спецификации; расхождение кода со
  спецификацией без эскалации пользователю.
- Порядок «спецификация → тесты → код»: тесты на поведение, отсутствующее в
  спецификации, — включая тесты, написанные до создания спецификации; код до
  тестов — нарушение порядка, проверяемое live-наблюдением процесса
  написания (как в правиле «Тесты перед кодом»), при ревью готового кода по
  диффу не репортится (ненаблюдаемо).

## 6. Границы применения

- Скилл — только для написания и ревью исходного кода: не для спек-документов
  и spec-driven изменений (скилл `spec`), не для проектной документации
  (скилл `docs`), не для TLA+-спек, TLC-моделей и доказательств (скиллы
  `tla-plus`, `tlc-run`, `tlaps`).
- Правила не выбирают алгоритмы, паттерны проектирования и архитектуру: они
  применяются к коду в рамках выбранного решения; работающее решение не
  переписывается ради правила.
- Форматирование и стиль — вне скилла: отступы, кавычки, порядок импортов,
  длина строки, именование идентификаторов — территория форматтеров,
  стайл-гайдов и конвенций проекта.
- Конфликт правила с явной конвенцией проекта — эскалация пользователю;
  тихая победа одной из сторон запрещена.
- Механические проверки кода — вне скилла: линтеры, статические анализаторы,
  тестовые раннеры и инструменты измерения покрытия запускаются своими
  средствами; правила скилла — требования к коду и чек-лист ревью, а не
  инструмент.
