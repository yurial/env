Не используй `sleep` в bash-командах ни в какой форме: ни отдельной командой, ни внутри составных конвейеров и циклов (`foo && sleep 5`, `timeout 5 bash -c 'sleep 2'`, `while ...; do sleep 1; done`). Что применять вместо: фоновые задачи инструмента (сборка, тесты, docker pull) — timeout-параметр инструмента или ожидание уведомления о завершении (`task notification`), а не опрос через sleep; завершение произвольного процесса по его PID — `tail --pid=<pid> -f /dev/null` (GNU tail с `-f` блокируется до смерти процесса и выходит rc=0; по уже мёртвому PID возвращается мгновенно). Флаг `-f` обязателен: без него `tail --pid=<pid> /dev/null` выводит warning `PID ignored; --pid=PID is useful only when following` и выходит сразу, не дождавшись процесса. Прямой вызов `sleep` дополнительно заблокирован permission-правилом bash.

Самым первым действием при начале новой задачи — до исследования, чтения файлов, планирования и любых правок — определи целевой репозиторий. Ключевое понятие — «целевая директория»: директория, над которой ведётся работа в задаче; она может не совпадать с cwd, из которого запущена сессия. Проще всего проверить submodule: `git -C <целевая директория> rev-parse --show-superproject-working-tree` — если вывел путь, целевая директория лежит в submodule (в обычном checkout'е). Ветка (worktree) создаётся на том уровне, на котором идёт работа: если изменения затрагивают только субмодуль — ветка создаётся только в субмодуле, суперрепозиторий не трогаем; если изменения затрагивают несколько субмодулей — ветка создаётся в каждом затронутом субмодуле и в суперрепозитории (в суперрепо фиксируются новые указатели субмодулей). Если команда ничего не вывела: (1) целевая директория — отдельный самостоятельный репозиторий, в том числе не связанный с окружающим git-проектом (untracked вложенный репозиторий), — worktree создаётся для него; (2) иначе целевой репозиторий тот, чьим toplevel является или внутрь которого входит целевая директория. Субмодули должны иметь remote, указывающий на удалённый репозиторий, а не на локальный путь: иначе ветки из субмодулей нельзя пушить/фетчить и суперрепо не сможет ссылаться на их коммиты. Создавай worktree по пути `~/wt/<repo>/issue-<name>` и ветку git с именем issue-<name> от актуального master целевого репозитория; <repo> — базовое имя toplevel целевого репозитория. Несколько целевых репозиториев в задаче — отдельный worktree на каждый, пути передаются сабагентам. Все дальнейшие действия задачи выполняй только в этом worktree: это исключает пересечение параллельно работающих задач в общем рабочем дереве. Worktree и ветку создаёт инициатор задачи (main); сабагенты работают в уже созданном worktree по инструкции.

При запуске агента первая строка текста задания обязательна: `Worktree: <абсолютный путь до worktree>`. У инструмента task нет параметра workdir — путь к worktree передаётся только текстом промпта; задание без строки `Worktree:` — ошибка делегирования, такое задание не запускай. По правилам assistant.md сабагент обязан первой командой показать `pwd`/`git rev-parse --show-toplevel`; до признания результата сверь этот вывод с ожидаемым worktree (а также по путям в командах и отчёте агента). Агент, выполняющий задачу не в выданном worktree, — ошибка делегирования: останови его и перезапусти с корректной Worktree-строкой.

- Не используй серии `grep ... | wc -l` / повторные обращения к логу для оценки прогресса фоновых задач (ya make, тесты, docker pull и т.п.). Если задача запущена в фоне — жди уведомления о завершении или `task notification`.
При генерации commit-message не добавляй "Co-Authored-By".
Если инструмент fetch завершился ошибкой запуска — используй локальный curl.
При запуске bash команд перенпрявляй stdout в /dev/null если явно не ожидаешь вывод. Если ожидаешь вывод, делай tee <file> | wc -l; tail -n <n> <file>; чтобы понимать размер файла. Читай <file> как тебе удобно. Запускать команду повторно для получения вывода запрещено. Только если уверен в малом размере вывода, запускать bash команду без перенаправления вывода. Не засоряй свой контекст лишним. Экономия контекста касается только stdout bash-команд, а не инструмента Read: файлы читай инструментом Read целиком (без limit/offset) — лишние повторные чтения частями дороже и медленнее полного чтения, контекст моделей большой (до 1M). Обрезку (offset/limit, tail) применяй только к заведомо огромным файлам, когда нужна конкретная секция.
Когда создаешь коммиты, всегда проверяй какие файлы ты коммитишь. Артефакты сборки, бинарники, симлинки и прочий мусор не должен попадать в коммит.
В качестве tmp директории используй ~/tmp/
Не удаляй ветку, пока она не будет смержена.
